# 市井（sim-game）

> 游戏合集里的一款，返回 [游戏柜](../../README.md)。

效用AI 驱动的生活模拟游戏原型 —— 借鉴《模拟人生》的需求驱动 AI
与《行会3》的生产链经济，两者共用同一套打分内核。

## 快速开始

```bash
open index.html      # 零依赖单文件，双击即可（仓库根目录下为 games/sim/index.html）

# 以下命令在仓库根目录执行
npm run dev          # 起服务：http://localhost:5173（首页是游戏合集）
npm run sprites      # 重新生成角色精灵并嵌回游戏（零依赖，Node 即可）
npm run check        # 跑全部回归（13 个，约两分钟）
npm run check -- farm   # 只跑名字里带 farm 的
npm run smoke        # 只跑冒烟测试
```

## 节奏调参（人物干活的快慢）

面板左上角的 `⏸ ▶ ▶▶ ▶▶▶` 改的是**现实时间**流速；觉得"人物干活磨蹭"通常不是它的事，
而是游戏内的工时和脚程。这两个数在 `index.html` 里并排放着，就在 `playerDur()` 上方：

| 常量 | 现值 | 作用 |
|---|---|---|
| `WORK_MUL` | `0.55` | 所有活计的时长倍率。伐木 90→50 分，木作 120→66 分，睡觉 240→132 分。<br>只压时长，**不动**产出与需求回复的总量 —— 同一个工时段能多干几件事，单件收益不变。 |
| `WALK` | `2.0` | 脚程，格/模拟分钟（玩家与 NPC 共用）。地图扩到 62×52 之后，横穿一趟的路上时间是大头。 |

想再快就把 `WORK_MUL` 往下调（`0.4` 约等于原速两倍半），想回到扩图前的手感设 `1` 和 `1.5`。

托管全员跑 14 天的对照（两次采样）：

| | 改前 | 改后 |
|---|---|---|
| 每人每天干成的活（work 区物件） | 3.1 / 3.6 件 | 10.6 / 8.2 件 |
| 半途改主意的比例 | 13.2% / 18.6% | 6.6% / 5.2% |
| 需求跌破 15 的次数 | 63 / 139 | 14 / 8 |

**顺带修的老账**：NPC 结算需求回复时分母用的是物件的名义 `dur`，而 `left` 早被手艺折扣缩过 ——
干得越快回得越少。工时倍率一上去这个 bug 会直接把人饿死，所以改成统一用 `variantDur`
（`tryInteract()` 那条玩家路径之前也没记 `variantDur`，一并补上）。

## 力气活：一下一下地抡

砍树、采石、采集、田里的活、木作 —— 这五样是「出力」的活。玩家做这些不再走进度条，
改成 **Minecraft 那种一下一下地落**：按一次 `E` 落一下（手机按一次「互动」，按住可连抡），
头顶的格子满了就成。NPC 照旧按工时慢慢磨 —— 他们不会按键。

| 活计 | 下数（空手 → 有工具） |
|---|---|
| 林地（砍） | 4 → 3（铁斧） |
| 采石场（凿） | 6 → 4（铁镐） |
| 田（锄） | 3 → 2（锄） |
| 木作坊（刨） | 6（手艺高了更少） |
| 野果丛（采） | 2 |

下数由这次的实际工时推出来：`swingsOf(vdur)` = `vdur / SWING_MIN` 夹在 2~8 之间。
于是**工具和手艺折的不再是「进度条走快一点」，而是少抡两下** —— 一把好斧头第一次是看得见的。

反馈三件套，缺一件手感就散：头顶的格子一下一格（连续的条会让人以为「等着就行」）、
人朝目标前倾一下再落回来、接触点崩几粒碎屑。起手那一下就直接落下去 ——
否则第一次按 `E` 什么都不发生，玩家会以为卡住了。

**代价算清楚了**：省掉的只有「等」。每抡一下都按它折合的工时补一份需求衰减，
所以砍一棵树掏空你的程度和走进度条时**分毫不差**（实测两条路径六项需求的变化量完全相同）。
不补这一份的话，世界的钟没为这件活走、人却一点不累，「睡一觉 → 秒砍六棵 → 再睡」
就能刷出无限木料。

调参：`SWING_MIN`（一下抵多少分钟工时，越小下数越多）、`SWING_CD`（两下之间的最小间隔，
也是长按连抡的节拍）。想让某类活也能抡，往 `LABOR` / `laborOf()` 里加一个标记就行。

## 柴：生产链的第一环

### 病灶

改之前，**全村木料存量恒为 0**。实测 7 天 1577 次决策，林地当选第一名 **2 次**（0.13%），
73% 的时候排在 12 名开外；木作坊因此 `pre` 恒 false，连候选都进不去，木器这条链整条是死的。

不是 bug，是打分结构。两层原因，两层都得治：

1. **木料只对着「家计」广播，而家计有地板。** `provision()` 里存粮那一项九份米就封顶，
   中位数常年 76，`urgency(76, 1.1)` 只剩 0.21 —— 林地那 26 分广播到手只有 5.5，
   还要扣掉 `cost:{energy:16, hygiene:12}`。而钓点广播 `provision:30` **+ `fun:32`**，
   cost 只有 `energy:8`。**fun 是私人需求、永远在掉、不会被别人填满，所以钓鱼永远有正分，
   伐木永远没有。** 单看收益伐木链其实不差（木器 48 文 vs 鱼 16 文，0.39 vs 0.33 文/分），
   输就输在钓鱼是「一边挣钱一边玩」，砍柴只挣钱。
2. **就算下游值钱，上游也领不到。** 效用 AI 只会问「这件事【现在】能不能做」，
   不会问「做了它，下一件事才做得成」—— 缺料的活被 `pre` 直接挡在候选之外。

### 两刀

**① 灶台烧一顿要一根柴（`mat:{wood:1}`）** —— 木料由此从「家计」挪到了「饿」这条
**永远不会饱和**的链上。没柴不等于饿死：米缸的冷食还在（hunger 38 对灶台的 78），
**柴决定的是吃得好不好，不是活不活得下去**。这条后路必须留着，否则第一天全村原地饿毙。
同时把柴堆算进 `provision()`（柴米油盐，柴排头一个）—— 光有传递不够，
那份传递的分数跟着**此刻**的饿劲走，而饿了才想起砍柴已经太晚，人会很合理地
就近抓一把冷食。家计里的柴堆才是「未雨绸缪」：柴见底，不饿也心慌。

**② 缺料传递（means-end chaining）** —— 缺料的活先按「假装料够了」算一遍分，
把这个分数打个折（`CHAIN_K = 0.9`）记到能供这份料的活头上：

```
灶台（缺柴，假装有柴能打 X 分）──× 0.9──▶ 林地（gives:{wood:5}）
木作坊（缺木料×2）            ──× 0.9──▶ 林地
```

关键是**加成落在距离/锚点折扣之前**：为了下一顿饭跑北山，那趟路该打的折一分不能少。
料一够，`matLack` 返回 null，加成自己消失 —— 不会砍上瘾。

配套：`mat` 必须和 `pre` **分开写**。「缺的只是料」是上游能解决的，
「没菜谱 / 今日已采尽 / 钱不够」不是；混在一起就没法传递。

### 结果（托管全员，同一套统计口径）

| 14 天 | 改前 | 改后 |
|---|---|---|
| 伐木 | 2 | 49 |
| 木作坊做木器 | 2 | 30 |
| 全村木料存量 | 恒 0 | 6~14 之间来回（真的紧俏） |
| 灶台 / 米缸 | 269 / 3 | 197 / 101（六成生火，四成将就） |
| 全村存粮 | 209 → 317 一路涨 | 51~74 平稳 |
| 需求均值 | 87 | 87 |
| 需求跌破 15 | 33 | 27 |

28 天长跑：无人饿死，需求均值 89，木料存量在 5~14 之间自己找平衡。
传递机制的开销实测为零（6.4 万步/秒，30 倍速只需要 480 步/秒）。

### 玩家自己怎么吃饭

```
钓鱼 / 采集 / 伐木→木作 ──▶ 集市卖钱 ──▶ 米铺籴米（一次三斗）──┐
自家田：播种(耗米1) → 浇水 → 收割(得4斗) ──────────────────┤
                                                          ├─▶ 灶台  生火做饭  hunger +78，费柴×1
                                                          └─▶ 米缸  取些冷食  hunger +38，不用柴
```

**柴决定的是吃得好不好，不是吃不吃得上。** 灶台的九道菜都要生火（一顿一根柴），
米缸的冷食不要 —— 所以最坏情况下的底线是「有米（或野果）就饿不死」，
柴只是把 38 抬到 78。

### 行囊

在这之前**玩家看不见自己身上有什么** —— 只有「家赀排名」里那行小字（`米N 柴N 器N`），
工具更是连显示的地方都没有（`toolNames()` 写好之后从来没被调用过，打了铁斧也无从确认）。
柴变成每顿饭都要查的数之后，这个缺口就不能留了。

面板米价下面加一节「行囊」，四行：

| 行 | 内容 | 规则 |
|---|---|---|
| 灶下 | 米 N　柴 N　+ 一句判断 | **永远显示**，为 0 标红 |
| 山货 | 野菜/野果/菌子/药草 | 有才露面 |
| 可售 | 木器/腌货/蛋/鱼/石料 | 有才露面 |
| 家什 | 已打的工具 | 空手时提示去木作坊 |

那句判断按四种状态给：`够生火做饭` / `有柴，缺配料` / `没柴，只能取冷食` / `没柴也没吃的`
—— 把「今晚吃得上吗、吃得好吗」压成一行，不用自己去心算。

物品名统一走 `INV_N`（和 `FORAGE` 放在一起），免得界面上两处各写一份。

### `want` 和 `pre` 必须分开

籴米广播的是常数 60，而 `provision()` 里存粮九份就封顶 —— **AI 感觉不到自己在囤**。
实测 14 天籴 423 份、做饭吃掉 390 份、田里又收 75 份，全村存粮 209→317 一路只涨，
钱全变成了米山。所以米铺需要一条「够吃四天就别再籴」的刹车（`RICE_ENOUGH = 12`）。

**但这条刹车一开始被写进了 `pre`，那是错的。** `pre` 同时管两件事 ——
NPC 要不要去、以及**玩家能不能用**。防囤积只该管前一件；写进 `pre` 就等于连玩家
一起锁上，站在柜台前会被顶一句「家里米还够」。而玩家囤米有正当理由：
播种一斗一颗、四时供奉每份要 `food×3`、义仓捐粮要两斗。

所以拆成两个钩子：

| 钩子 | 管什么 | 谁受影响 |
|---|---|---|
| `pre` | 这件事**做不做得成**（钱不够、没菜谱、今日已采尽） | AI 和玩家都挡 |
| `mat` | 缺的只是**料**（上游能解决 → 参与缺料传递） | AI 和玩家都挡，但会往上游传分 |
| `want` | AI 的**自觉**（够了就别再来了） | 只压 AI 的打分，玩家照用 |

以后再加「差不多得了」这类规则，一律挂 `want`。

### 冷食为什么不能只认米

烤鱼那行的原注释是「**不用米** —— 这是断粮时的后路，也是钓鱼存在的第一个理由」。
加了柴之后这条后路变成了「不用米，但要柴」，于是手里攥着一把野果、灶下没柴的人
反而得先跑一趟北山。所以米缸改成 **米或野果都能取**（有米先吃米）——
柴可以让你吃得差，不该让你吃不上。

### 还没解决的

- **采石场仍然没人去（28 天 0 次）**。石料唯一的出口是兴造，而兴造是玩家的事 ——
  NPC 那边没有任何消费者，所以传递机制无料可传。要么给石料补一个 NPC 用得着的去处，
  要么接受它就是玩家资源。
- **钱没有下水道**。木器卖了钱，钱除了籴米（现在还封了顶）和聘礼/馈赠之外没处花，
  28 天里人均从 125 涨到 174。不致命，但村子会慢慢变成守财奴。

## 合成：一张表，一个面板

合成一直是有的 —— 灶台九道菜、木作坊的木器和五件家什、腌坛、十种兴造，一共 25 条。
但它不像个系统，因为两件事：

1. **看不见。** 不站在木作坊前，你不知道它能打铁斧；不建腌坛，不知道腌坛做什么。
   泰拉瑞亚正相反：合成栏永远开着，列出此刻能做的一切，靠近工作台就多出条目。
2. **配方硬编码在物件上。** `menuList()` 里一串 if-else，加一条要改三处 ——
   **没有统一的数据结构，就长不出统一的界面**。这是根因。

### `CRAFT`：那份索引

数据仍然各归各处（菜在 `RECIPE`、家什在 `TOOL`、兴造在 `BUILD`），`CRAFT` 只做索引：

```js
{ id, n, st, need:{...}, money, out, tip, recipe?|tool?|build? }
//        ↑ 在哪做：stove 灶台 / bench 木作坊 / crock 腌坛 / yard 自家院 / town 镇中心
```

关键是 **`craftLack(s, c)` 是「能不能做」唯一的判据** —— 合成面板、工作台菜单、
缺料提示全问它。三处各写一份判断迟早会对不上（T26/T27 的菜谱和供奉就是这么丢的）。

灶台和木作坊的菜单现在由 `craftMenuRows()` 从 `CRAFT` 生成，if-else 分支删掉了。
以后加配方只改一处，面板和菜单同时出现。

### 合成面板（`C` 键 / 触屏「合」）

```
合成　柴/木 14 · 石 8 · 180 文
 1. 木器（木料2）                  可做
 2. 锄（木料3·40文）               可做
 …
12. 家常饭（柴1·米2）             去灶台
13. 菜饭（柴1·米1·野菜1）          缺 野菜1
▼ 1/25　↑↓ 选择　Enter 确认　Esc 取消
```

- **能做的排在前头，做不了的留在后面**（灰着，但看得见 —— 看不见正是老问题）
- 右边一列只说三句话：`可做` / `去灶台` / `缺 野菜1`
- 选中就做：兴造进兴造模式，工作台配方**直接开工**（省掉「走过去→按 E→在菜单里找」）
- 选中做不了的，把那句理由甩成浮字，不再默默无反应
- 打过的家什自动从表里消失

同一份木料，灶下叫**柴**、案上叫**木料** —— `matName()` 让名字跟着用途走。

顺带给 `drawMenu()` 加了滚动窗口（`menu.top`）：25 条一次全画会顶穿视口。
所有菜单共用这条逻辑，以后配方再多也不会溢出。

### 顺带修的：菜谱那一列 hunger 原来是摆设

吃饭回复的饱腹取的是**灶台物件**那个固定的 `adv.hunger:78`，`RECIPE` 里每道菜声明的
hunger 只喂给 `bestRecipe()` 排序 —— 烤鱼(66) 和八宝饭(100) 吃下去一模一样。
不修的话，加再多菜谱也吃不出区别。

改法：`advOf(s)` 在行动结算时用**这次这道菜**的 hunger 顶掉灶台的固定值；
NPC 出门前就用新的 `plan` 钩子把菜定下来（`plan:s=>bestRecipe(s)`），
否则他们回到灶前才挑，行动过程中没法按菜谱回复。料在路上被抢走时退一道能做的，
不至于白跑。

实测（饱腹从 0 起，吃一顿）：

| 菜 | 声明 | 实际 |
|---|---|---|
| 稀粥 | 44 | 41 |
| 野菜团 | 58 | 55 |
| 烤鱼 | 66 | 63 |
| 家常饭 | 72 | 69 |
| 菌鱼羹 | 82 | 79 |
| 腌菜饭 | 88 | 85 |
| 八宝饭 | 100 | 97 |

差的那 3 点是做饭那 27 分钟里自然掉的（0.10/分），对得上。

### 还没做的：合成树只有一层

木料→木器就到头了，没有中间材料（木板、石砖、麻绳），工具也是一次性的五件、
没有铜→铁→银的递进。Minecraft 是三层、泰拉瑞亚更深。要做那个是另一档改动，
而且会牵动经济平衡 —— 木料现在刚好卡在柴上，再加一道工序得重新调产量。

## 参考饥荒的三样

### 一、吃的放不住

`SPOIL` 里的东西每天烂掉一部分：兽肉 0.5、鱼 0.45、山货 0.22、药草 0.16、蛋 0.20。
**米不坏**（谷物本来就是为了存），**腌货不坏**（腌的意义就在这），木石不坏。
小数用累加器攒着，一条鱼一天不会坏掉"0.45 条"，攒够一整份才真的少一份。

这一刀顺手给三样东西补上了它们本来就该有的理由：

| | 以前 | 现在 |
|---|---|---|
| 腌坛 | 卖钱的小玩意 | 唯一能把山货**存下来**的办法 |
| 谷仓 | 只抬家计上限 | 兼任饥荒的冰箱：腐坏减到三成 |
| 集市 | 有空去卖 | 手里的鱼是烫手的，今天不卖明天少小半 |

实测（一天 / 五天）：鱼 10→6→1，兽肉 4→2→0，野菜 8→7→3；米和腌货纹丝不动。
有谷仓：鱼 10→5、野菜 8→6（五天）。**八宝饭那种跨季攒料的大菜，没谷仓就是攒不住**
——上一轮定的"跨季大菜"由此有了前置条件，而不是一句空话。

### 二、手艺解锁配方

饥荒的科学机器在这里换成**手艺**（生手→学徒→匠人→好手→巧匠→大匠→宗师）。
41 条配方第一天全开等于没有长期目标；而手艺此前只管工时/售价/精品，也没有目标感。
把两者接起来 —— **手艺涨一级，合成表上多亮几行**。生手时 26 条锁着，宗师时全开。

`CRAFT_LV` 是一张按名字索引的小表，级别写回各自的源表（`RECIPE` / `TOOL` / `BUILD`），
所以 `canMake()` 和 `buildCheck()` 就地能查。**这一条对全村生效**：NPC 的 `bestRecipe()`
走的就是 `canMake()`，手生的人做不出腌菜饭和八宝饭。

### 三、野物与打猎

饥荒把"出门"变成一个有代价的决定。这里照搬那个意思，但**收在北山**（`y < HILL_Y`）：
镇上和自家院里永远安全，危险只在山上。这不是偷懒 —— 给全图铺一层压力只会让人不敢动；
把危险钉在一片地上，"今晚上不上山砍柴"才成为一个真的选择。那一带正好是林地、采石场、野果丛。

| | 血 | 脚程 | 一口 | 掉落 |
|---|---|---|---|---|
| 野狗 | 3 | 2.5（比人快） | 体质 −5 | 兽肉1 兽皮1 |
| 山猪 | 6 | 1.5（跑得掉） | 体质 −10 | 兽肉2 兽皮1 |

**只在夜里和冬天下山**：春夏白天一只都没有；冬夜最多四只。出没走确定性哈希，不用 `Math.random`。

打野物**和砍树是同一套手感**：连按或按住 `E`，一下一下地打。空手一下一血，
**猎叉**（木3·50文）一下两血，**皮甲**（木2·兽皮3·40文）挨咬伤减一半。
兽皮不坏、34 文，是打猎真正的进项；兽肉 26 文但坏得最快，当天就得处理 ——
所以有了**烤肉**和**肉羹**两道菜。

NPC 不打，只躲和跑：`score()` 里山上的活整体降权（近处 4%、远处 12%），
挨过咬的往山下跑（`s.flee`）。远处只压到 12% 是有意的 ——
家计真见了底的人还是会硬着头皮上山，那一趟才是有分量的故事。

**冬天七天的实测**（托管全员）：40 只下山、8 次咬人、体质最低 80、无人死亡、
伐木仍有 24 次。春天七天：19 只下山（只有夜里）、**0 次咬人**。

### 三个都踩过的坑

1. **野物不寻路，但不能一头撞死在树上。** 最早写的是"两个轴都走不动才算撞死了"——
   人和狗同一列时 dx≈0，目标 x 就是当前 x，`free(nx, b.py)` 恒为真，
   "撞死了"永远不成立。实测追 3 格追了 750 模拟分钟。改成看"实际挪了没有"，
   又变成挪一步被拉回来一步地来回蹭。**判定"卡住"很难写对**；
   最后换成 `beastGo()`：把想走的方向依次拧 0°/±52°/±103° 试，第一个通的就走，
   偏向哪边由 `b.side` 定死 —— 没有"卡住"这个判定了。各种地形都是 1.5~4 分钟。
2. **怕要怕整片山，不是怕野物脚下那几格。** 只压附近的话，人照样往山的另一头去，
   走着走着就撞上。冬天一周被咬 47 次、有人体质掉到 39。压整片之后降到 8 次。
3. **老存档没有后加的 inv 键。** `s.inv.meat++` 在 `undefined` 上会变成 NaN，
   一路污染到卖价和面板。读档时过一道 `fixInv()` 补齐。

## 开局无家：从一块空地起家

第 0 块地不再盖房、不再围篱笆、地上什么都没有 —— **榻、灶台、米缸、田、树，全要自己造**。
其余五户照旧有屋有院：这是个市井，不是荒岛；有对照才看得出你在从头起家。

开局身上：**米 4 · 柴 3 · 60 文**。第一件事是上北山砍柴，回来把榻立起来（木6·10文）——
没有它你晚上只能熬着。

| 新增兴造 | 料 | 说明 |
|---|---|---|
| 榻 | 木6·10文 | 最便宜、也最急。手艺 0 级就能造 |
| 米缸 | 木4·10文 | 囤米，取冷食（不用柴） |
| 灶台 | 木6·石3·20文 | 生火做饭。饱腹 78 对冷食的 38 |
| 树苗 | 木2·15文 | **六天后长成一棵真林地** |

### 只要是草地就能盖

以前「只能建在自家院里」这条规矩其实是**地形定死的** —— 草地只长在六户院子里，
别处兜底是夯土。所以改这条规矩得先改地：`FLOOR` 的兜底从夯土改成草地，
宅子之间的空档、镇子边上的边角，一下都成了能落脚的地方。全图 1468 格草地，
其中 **508 格可盖**（扣掉别人家的院子）。

判定也跟着换：`inMyYard` → `canBuildAt = isGrass && !inNeighborYard`。
唯一的禁令是别人家的院子；镇上的东西（凉亭、义仓）仍然只能在镇中心广场。
开垦（新田）走的是同一条规矩，所以**草地随处可垦**。

### 种树：价值不在产量，在位置

树苗的性质全做成 getter，随天数自己变 —— 不用另开一个 tick：

```js
get tree(){ return up()?1:0; }            // 成材了才是力气活、才能抡
get gives(){ return up()?{wood:5}:null; } // 成材了才进缺料传递
get pre(){ return up()?null:(()=>false); }
get art(){ return up()?'tree':'sapling'; }
```

砍它和砍山上的树一样多（+5），**差别在位置**：家门口的柴，冬夜的野物够不着。
六天的等待就是这份安全的价钱。

**存档要存下栽种那天**：`BUILT` 的记录本来只有 `{key,x,y}`，读档时 replay 一遍 ——
树苗的 `planted=day` 会被重置成读档当天，树永远长不大。加了 `d` 字段，
`placeBuild(key,x,y,replay,dayAt)` 把当初那天传回去。实测第 1 天栽、第 9 天存读，
树还是林地。

### 托管模式还活得下去

`decide()` 不会兴造，所以托管的无家玩家理论上会饿死。实测 14 天：**没死**，
饥饱 57~82、体质满值 —— 靠的是镇上的公共去处（竹榻歇脚、茶棚吃茶、浴堂茅厕）。
露宿街头，凑合着过 —— 这个结果本身就挺市井的，所以没有特意去改。

### 顺带修的

- `EXTRA` 原先按 id 索引（`bed1`~`bed6` 六条一模一样的「小憩」），
  自己造的榻 id 是 `bd1`，拿不到。改成按 `art` 索引，一条顶六条。
- 灶台的菜单判定原先是 `o.id.indexOf('stove')===0`，自己造的灶台 id 是 `bd2`，
  对不上 —— 改成认 `o.stove` 标记。**凡是"按 id 前缀认物件"的地方，
  一旦物件能被玩家造出来就会失效**。
- 山上林地的 `gives` 还写着 `{wood:2}`，是上一轮把产量提到 5 时漏改的
  （值只当键用，不影响逻辑，但读着是错的）。

## 钱的下水道

以前钱只进不出：木器、兽皮、腌货卖了钱，NPC 除了籴米（还封了顶）和聘礼、馈赠之外
没处花 —— 实测 28 天人均从 125 涨到 174。**「守财奴」不是玩法，只是一个没人管的数字。**

下水道开在**公共去处**上：市井里洗澡要澡钱、吃茶要茶钱，本来就该收。
但两处的收法不一样，差别是这一节里最要紧的东西：

| | 收法 | 为什么 |
|---|---|---|
| 浴堂 5 文 | **设闸**，没钱进不去 | 有免费的退路：水井打水（洁净 38 对浴堂的 88）。<br>于是穷人自动退到水井 —— 贫富差第一次能被**看见** |
| 茶棚 6 文 | **不设闸**，有钱添碗茶、没钱白坐 | 这游戏的内核是人跟人的关系，**不能卡在钱后面** |
| 茅厕 / 水井 | 免费 | 内急掉得最快，收钱等于罚款 |

### 茶棚为什么不设闸：一次量出来的教训

一开始茶棚也是设闸的。实测**挡掉了 22% 的社交，而且外向的人被挡得更多**
（茶棚被钱挡住：全 E 15%，全 I 6%）—— 正好把 MBTI 那条「E 比 I 社交多」的
涌现信号压平。改成「有钱添碗茶，没钱白坐」之后：位子不要钱，钱照样从手头宽裕的人
身上流走，**而且流的正是富人**（穷人本来也付不起）—— 那一头恰恰是原来最缺下水道的。

### 「先顾肚子」

效用 AI 只比较此刻的分数，不会自己留钱。不管的话它会把六十文开局全花在澡堂茶棚上，
第三天买不起米。`canAfford()` 补了两道家用常识：

1. **家当没置办齐，闲钱先留着安家** —— 没个窝就别先进澡堂
2. **家里没米，花完还得买得起一份米**

### 顺带补完的：托管会给自己立窝

「开局无家」+「decide() 不会兴造」= 托管的玩家永远没有榻、没有灶台、没有米缸。
茶棚一收钱他就顶不住 —— 冒烟测试里 `starving` 冒出来的就是他，
守着 **12 斗米和 3 根柴饿肚子**（有粮有柴，没锅没缸）。

`autoHomestead()` 补上这条：托管时缺什么就自己立什么，顺序是
**米缸 → 榻 → 灶台**（米缸最便宜，而且直接解决吃饭 —— 守着米没缸取比没床睡要命）。
**每 5 模拟分钟问一次，不是每天问一次**：只在跨日时问的话，第 1 天买了米也没缸取，
饥饱当天 17 点就见底。料不够时只做几次比较就返回，扫格子的开销只在真造得起时才付。

开局家底的柴也从 3 提到 5 —— 刚够立起第一件家当（米缸 木4）。给 6 的话，
教程第 4 步「弄够六根柴」开局就自动打勾，砍树那一课就白教了。

### 结果与残留

42 天托管：中位钱在 5~93 之间来回而**不再单调上涨**，水井第一次被用起来（283 次），
需求均值 86、洁净 89、交游 90、无人死亡。

**残留**：长跑到第 5~6 周，顶端还能攒出一点「死钱」（超过 118 文的部分，
`provision()` 里钱的贡献到 118 就封顶，再多毫无用处）。试过把价钱提到 8/10，
死钱从 141 降到 36，但需求均值从 86 掉到 77、洁净 89→80、交游 90→76 ——
**为了烧掉那点闲钱去折腾所有人的日子，不划算**。价钱在 `PRICE` 一行，想调随时。

### 这一轮把套件从 8 绿 5 红修回 13 绿

前面几轮改了不少设定，测试是照着老设定写的。逐条对下来，**红的全是断言过期，
没有一条是游戏真的坏了**（唯一的例外是手艺闸把教程卡死，那个在游戏侧修了）：

| 脚本 | 为什么红 | 怎么改的 |
|---|---|---|
| smoke-test | 「私田人手一块」—— 玩家的田要自己开了 | 不变量改成「除玩家外每户一块」 |
| verify-farm | 同上；`field1` 是玩家原来那块 | 同上；改用邻居的 `field2` |
| verify-build | 整块 ② 测「只能建在自家院里」；⑦ 测「院门封死」 | ② 改测「草地才行」；⑦ 换成【把自己砌死】—— 那才是这道闸真正防的事 |
| verify-tool | `jar1/stove1/field1` 不存在了；`PC.act.left=0` 跳不了结算 | 先自己造出这三样；改用 `finishAct()` |
| verify-life | 取「玩家继承来的榻」 | 改用邻居的榻测同一条产权规则 |
| verify-save | 存档版本写死 `v:12` | 改成 `v:SAVE_VER` |

**三条留下来的教训**（都在测试里写了注释）：

1. **别写死数量。** 「恰好十样兴造」「私田恰好六块」这类断言，加一样内容就假红。
   要守的是不变量（每一样都有画法、每户一块），不是当时的数字。
2. **别写死版本号。** `v:12` 那条测的是"阵容对不上不该崩"，不是"版本 12 能不能读"。
3. **`PC.act.left = 0` 不再等于"跳到结算"。** 力气活是一下一下抡出来的，
   根本不走计时那条路 —— 统一用 `finishAct()`。

顺手让冒烟测试**报出红了哪几条**（`FAIL[farm]`），以前只有一个光秃秃的 FAIL，
得回去人肉读代码才知道哪儿断了。

### 三个踩过的坑

**0. 手艺分级把教程卡死了。** 分级是先于教程写的，两边一撞：第 12 步「开一块田」要新田、
第 14 步要树苗，都是手艺 1 级；而**前 11 步一点手艺也挣不到** —— 砍树采石都不涨手艺，
只有钓鱼／木作坊／书塾涨。新手会停在 12/15 干等。两头一起改：
起家和教程用到的（榻/米缸/灶台/新田/茅厕/树苗）一律 0 级；
**砍树和采石也开始长手艺** —— 抡了一天斧头还是「生手」本来就说不过去。
现在四棵树到 1 级。



1. **差事必须只进不退。** 好几条的判据是「手里有多少料」，而下一步往往正好把那些料花掉 ——
   造灶台要三块石料，正是第 9 条刚让你凑的；造榻花掉的六根柴，正是第 4 条刚让你砍的。
   落成的那一刻进度会退回上一条，读起来像做废了。加了 `_qMax` 记最远进度，
   **而且要进存档** —— 读档后按当前物资重扫一遍，同样会退。
2. **完成判据分两种。** 状态看得出来的（手里几根柴、名下有没有榻）直接查；
   一次性的动作（睡过、做过饭、卖过东西）挂在 **`EV_SUBS`** 上记标记 ——
   事件流本来就是这游戏的叙事通道，口子是现成的，**不用往砍柴、做饭、卖货各处塞回调**。
   只有「走过两步」和「开过合成」没有事件，就地记了两个标记。

### 顺带修的两处文案

- `行囊` 的「灶下」那行原来只看柴和配料，一个**连灶台都没造**的人也会被告知「够生火做饭」。
  改成先看有没有灶台/米缸。
- 建造事件原来写「在自家院里起了一座…」—— 现在哪块草地都能盖，地点不该写死。

## 玩法：一个主角 + 三个 AI

你直接操控 **小满**，其余三人由效用 AI 自主生活。

| 操作 | 作用 |
|---|---|
| `WASD` / 方向键 | 自由移动（连续位移，不是格子跳跃） |
| `E` / `空格` | 与脚下发光格子上的物件交互；力气活是**连按/按住抡**（见上节） |
| `ESC` | 中断当前行动 |
| `T` | 把主角托管给 AI（模拟人生式的"自由意志"） |

**移动会打断正在做的事**——这是刻意的：让"要不要坚持做完"成为一个决策。

### 交互菜单

走到 **NPC** 旁边（会出现青色光圈）按 `E`，弹出社交菜单：

| 动作 | 关系 | 说明 |
|---|---|---|
| 闲聊 | +3 | 安全牌 |
| 称赞 | +6 | 涨得快一点 |
| 开玩笑 | +1 / +9 | **关系 <30 时会冷场**，熟了才有效 |
| 深聊 | +14 | 需要关系 ≥ 40 |
| 送礼 | +20 | 花 15 金币 |
| 争吵 | −16 | 自己出口气，对方掉需求 |

关系变化会以**浮动文字**即时反馈。人的优先级高于物件——站在物件上但旁边有人时，
按 `E` 是找人说话。

**物件**有多种做法时也会弹菜单（床：睡觉 / 小憩；书架：看书 / 钻研；沙发：看电视 / 发呆），
只有一种做法的物件按 `E` 直接执行。变体动作只回一部分需求，也**不结算生产链产出**。

### 同一套打分，两种用途

效用 AI 对 NPC 是**决策**，对玩家是**建议**：

- NPC：算完分直接执行最高分的行动
- 玩家：算完分显示在面板上，你可以完全无视

这样玩家和 NPC 活在同一套规则里，但保留自主权。面板上点任意 NPC
可以看它此刻的打分排名——**你能看见它在想什么**。

> 无人值守跑模拟（比如冒烟测试）时必须先开托管，否则主角会站着饿死。
> 这不是 bug，是手动操控的必然结果。

## 核心设计：效用 AI + 智能物件

物件不被 AI「认识」——**物件主动广播自己能满足什么需求**。
角色只做一件事：给所有广播打分，挑最高的。

```
分数 = Σ(广播量 × 紧迫度^p × 性格权重) ÷ 距离折扣
```

加新玩法不用改 AI，只需在 `OBJ` 数组里加一条数据。

生产链靠**前置条件**自然串联，没有任何硬编码的步骤顺序：

```
林地(无条件) → 工作台(需木材≥2) → 摊位(需家具≥1)
            → 粮店(需金币≥24) → 炉灶(需食物≥2)
```

### 渲染插值：模拟步长 ≠ 渲染帧率

模拟走**固定步长**（0.25 模拟分钟一步，1x 时 16 步/秒），渲染走 **60fps**。
两者频率不同，如果直接拿模拟位置去画，每步的位移会在一帧内跳完——
逻辑完全正确，但看起来是「一格一格闪现」。

解决办法是每步记录上一次位置，渲染时按 `accSim / SIM_DT` 在两步之间插值：

```js
const alpha = accSim / SIM_DT;
s.rx = s.ppx + (s.px - s.ppx) * alpha;    // 渲染用 rx/ry，不是 px/py
```

实测：模拟位置每帧最大跳 9px、只有 26% 的帧在动；
插值后每帧最大 2.4px、98% 的帧都在动。

两个配套注意点：

- **瞬移必须同步 `ppx/ppy`**，否则角色会从旧位置"滑"过整张地图
- **深度排序也要用插值位置**，否则前后遮挡关系会抖

### 三个已经踩过的坑（改动 AI 前务必读）

1. **决策抖动** —— 不能用「需求低于阈值就打断」。两个需求同时告急时角色会无限
   横跳，一件也做不成。必须用**迟滞切换**：定期重估，新方案要显著更优才换，
   且当前行动带惯性加成。

2. **事务原子性** —— 需求是连续填充的，但资源只在行动**完成**时结算。
   角色吃饱就中途跑掉会导致食物永不减少。**带产出的行动必须不可中断**。

3. **驱动力不能归零** —— 经营类需求（家计）满值后角色会集体躺平坐吃山空，
   必须给它设一个不会归零的地板。

## 角色：逐像素画的部件组合

角色不是画出来的，是**算出来的**——但算的方式是**逐像素**，不是矢量缩图。
之前那版用「矢量画 → 12 倍超采样 → 缩小 → 吸附调色板 → 描边」，缩下来
之后脸上一块大阴影、瞪着圆眼、头发糊成一团，人像一颗土豆。现在的
[`tools/character_gen.js`](../../tools/character_gen.js) 在 32×42 的逻辑画布上一个点一个点地画，
再 ×3 放大成游戏要的 96×126 一帧。一个逻辑像素正好等于地面的 3px 颗粒，
整张画面的像素密度一致，这是它看起来"像一款像素游戏"而不是"贴了张图"的关键。

```
角色 = 体型(build) + 肤色 + 发型(hairstyle) + 刘海(fringe) + 五官 + 服制(outfit) + 头饰(cap) + 配色
```

头一律 14×13，靴子踩在同一条地平线上，体型只靠躯干宽度、腿长和是否佝偻来区分：

| 体型 | 特征 |
|---|---|
| `std`   | 标准，躯干 12 宽 |
| `slim`  | 瘦，躯干 10 宽、腿细 |
| `stout` | 壮，躯干 14 宽、腿粗 |
| `young` | 矮两格的少年 |
| `elder` | 矮两格 + 缩脖子，配拐杖和长须 |

可换模块：眼形 `round/big/smile/squint/beady`（瞳孔一律朝右，翻转贴图后就朝左，
和面朝方向一致）、嘴形 `smile/grin/small/line/frown/pout`、
发型 `short/long/twintail/bun/topknot/spiky/ponytail/bald`、
刘海 `straight/side/middle/messy/up`、服制 `ruqun/changshan/daopao/duanda`、
头饰 `zan/jin/scarf/flower`，另有眉、胡子、鼻、腮红、耳朵、拐杖开关。

走路四帧是 `站 / 左脚抬 / 站 / 右脚抬`：抬脚那两帧身子上浮 1px，
手臂和裙摆反向摆 1px。描边是最后一步对整个剪影做四邻域膨胀，
所以任何部件都不用自己操心描边。

图集 16 行：前 6 行是手写的六位主角（顺序 = 游戏里 `NAMES`），
6~15 行按确定性哈希从部件库里生成。游戏里存的只有行号，
所以这些行的样子一旦发布就不能变——要加新脸只能往后追加行。

```bash
npm run sprites                      # = node tools/character_gen.js --embed
node tools/character_gen.js          # 只出 assets/sprites/cast96.png 和预览，不改游戏
```

零依赖：PNG 编码是脚本自己写的（zlib 是 Node 内置），不再需要 pillow / numpy。

### 画像素小人的三条经验

1. **一个色只能有一个意思。** 鞋子原来和描边同为深棕，缩在一起就是脚下一条黑带，
   人像悬空。鞋面提亮一档，脚立刻落地。
2. **高光要在受光侧。** 发色的亮色曾经被当"背光"铺在右侧，整头发看着像贴了一块补丁。
   亮色只在左上角点两三格，暗面用本色就够了。
3. **下摆别遮住腿。** 袍子一路垂到鞋面，人就没有"站着"的感觉；留两格露出小腿，
   剪影才立得住。
