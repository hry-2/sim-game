# 独立游戏 GitHub 授权配置指南

> 本文为工程实践参考，不构成法律意见。涉及公司雇佣关系、发行合同、
> 版号申请等实质问题时，请咨询执业律师。

---

## 零、开始之前：先确认这个项目"属于谁"

这一步比选许可证重要得多，也最容易被跳过。

《中华人民共和国著作权法》第十八条第二款明确将**计算机软件**列为特殊职务作品：

> "主要是利用法人或者非法人组织的物质技术条件创作，并由法人或者非法人组织
> 承担责任的工程设计图、产品设计图、地图、示意图、**计算机软件**等职务作品……
> 作者享有署名权，著作权的其他权利由法人或者非法人组织享有。"

同条第三款还规定："法律、行政法规规定或者**合同约定**著作权由法人或者
非法人组织享有的职务作品"，同样归单位。

**换句话说，如果这个项目和你的本职工作沾边，或者你用了公司的设备、
网络、账号来做，著作权很可能不是你的。** 而且很多公司的劳动合同、
保密协议、竞业协议里有更宽泛的知识产权归属条款，约定优先于法律默认规则。

### 建议的隔离动作

| 项目 | 做法 |
|---|---|
| GitHub 账号 | 用**个人邮箱**注册的独立账号，不要用公司邮箱或公司组织下的仓库 |
| 设备 | 个人电脑，不使用公司发放的设备 |
| 时间 | 非工作时间 |
| 网络与账号 | 不使用公司 VPN、公司订阅的付费工具、公司云账号 |
| 合同 | **先翻一遍**你签过的劳动合同和知识产权/竞业条款 |
| 留痕 | 保留能证明创作时间与环境的记录（commit 时间戳本身就是证据） |

> 如果条款存在争议空间，最稳妥的做法是在启动前和公司签一份书面确认，
> 明确该项目归你个人所有。事后再谈会被动得多。

## 一、核心概念：公开 ≠ 开源

**不放 LICENSE 文件 = 保留一切权利。** 别人在法律上不能复制、修改、分发你的代码。

但要注意 GitHub 服务条款 D.5 的例外：仓库设为公开后，你授予其他 GitHub 用户
"a nonexclusive, worldwide license to use, display, perform and reproduce (by forking)"
——也就是**其他用户可以在 GitHub 平台内查看并 fork 你的仓库**。

这个授权只在 GitHub 平台内部有效，不允许他们拿去改改上架卖钱。
但代码事实上已经被复制出去了，撤不回来。**不想让人看到，就设为 Private。**

---

## 二、最关键的一条：代码和资产必须分开授权

这是独立游戏授权最常见的致命错误。

如果你在仓库根目录放一个 MIT LICENSE，它字面上覆盖整个仓库——
**任何人都可以合法地拿走你的美术、音乐、剧情，改个名字上架 Steam。**
MIT 明确写了 "including without limitation the rights to use, copy, modify,
merge, publish, distribute, sublicense, and/or sell copies"。

正确做法是**双授权**：

```
your-game/
├── LICENSE                    ← MIT / Apache-2.0，仅覆盖代码
├── LICENSE-ASSETS.md          ← 专有，保留一切权利
├── THIRD-PARTY-NOTICES.md     ← 第三方合规台账
├── src/                       ← 代码，受 LICENSE 约束
├── tools/                     ← 生成脚本，受 LICENSE 约束
└── assets/                    ← 美术/音频/剧情，受 LICENSE-ASSETS 约束
```

并在 README 顶部用一张表说清楚哪个目录归哪个许可证管。

## 三、按目标选方案

| 你的目标 | 仓库可见性 | 代码许可证 | 资产许可证 |
|---|---|---|---|
| **纯商业，代码不公开**（最省心） | Private | 不放，或放 All Rights Reserved | 同左 |
| **想公开代码攒口碑，但游戏要卖钱**（推荐） | Public | MIT 或 Apache-2.0，仅 `src/` | 专有，保留一切权利 |
| **希望别人能看能学，但不能拿去卖** | Public | PolyForm Noncommercial / BSL 1.1（**非 OSI 开源**） | 专有 |
| **彻底开源，做社区项目** | Public | MIT 或 Apache-2.0 | CC BY 4.0 或 CC0 |

### MIT 还是 Apache-2.0？

- **MIT**：更短、更常见、心智负担低。个人小项目够用。
- **Apache-2.0**：多了**明确的专利授权**和**商标条款**，还要求标注修改。
  如果项目可能商业化、可能有公司参与、或你在意专利风险，选它更稳。

### 请避开 GPL

传染性会强制下游开源，且历史上与 iOS App Store 的分发条款存在冲突
（DRM 与 GPL 的附加限制条款不兼容）。商业游戏不要碰。

### "Source Available" 不是开源

PolyForm Noncommercial、Business Source License (BSL) 这类许可证
允许别人看源码、学习、贡献，但禁止商业使用。它们**不被 OSI 认定为开源许可证**，
用的时候不要对外宣称"本项目开源"，容易招社区反感。

## 四、第三方素材：独立游戏真正翻车的地方

许可证选错最多是麻烦，第三方素材用错是**直接被下架或索赔**。

### 高风险清单

**字体 —— 最高频的雷区。**
"免费下载"≠"允许嵌入游戏分发"。绝大多数免费字体的授权只覆盖
桌面排版（desktop use），不包含 embedding。做游戏必须确认授权明确包含
**嵌入**和**商用**两项。安全选择：SIL Open Font License (OFL) 的字体。

**音频。** CC BY 必须署名；CC BY-**NC** 完全不能用于商业游戏；
CC BY-**SA** 会要求衍生作品同样开放，对闭源游戏是陷阱。

**引擎与库。** Phaser、Godot、PixiJS 都是 MIT，可以商用，
但**必须保留版权声明**——游戏内要有可访问的"致谢/开源许可"页面。
这一步几乎所有独立开发者都会忘。

**生成式 AI 素材。** 部分发行平台（如 Steam）在提审时要求披露
AI 生成内容的使用情况，需如实填报。

### 建立台账的纪律

每引入一个依赖或素材，**当场**登记到 `THIRD-PARTY-NOTICES.md`，
并把授权页面截图或授权邮件归档到 `docs/licenses/`。

三年后有人找上门时，你不会记得那个音效是从哪下的。

## 五、国内发行的额外事项

| 事项 | 说明 |
|---|---|
| **软件著作权登记（软著）** | 上架国内应用商店、申请版号的前置材料。中国版权保护中心办理，个人可申请 |
| **游戏版号** | 在中国大陆商业发行网络游戏的强制许可（新闻出版署审批）。**个人无法申请，必须通过有出版资质的公司** |
| **免费出海** | itch.io、Steam 海外发行不需要版号；Steam 中国区（蒸汽平台）需要 |

> 版号是国内独立游戏最大的现实约束。很多个人开发者的路径是：
> 先出海验证，或与有资质的发行商合作。

## 六、动手步骤

```bash
# 1. 仓库先设为 Private，等确定要公开再改
gh repo create your-game --private

# 2. 放置授权文件
cp LICENSE-CODE-MIT.txt        LICENSE
cp LICENSE-ASSETS.md           .
cp THIRD-PARTY-NOTICES.md      .
cp .gitignore .gitattributes   .

# 3. 全局替换占位符
#    <你的姓名或工作室名>  <你的邮箱>

# 4. 目录分离
mkdir -p src assets tools docs/licenses

# 5. 首次提交前，确认没有密钥被纳入
git add -A && git status
```

> 也可以用 GitHub 网页端的 "Add file → Create new file → LICENSE"，
> 它会弹出官方许可证模板选择器，自动插入准确全文（Apache-2.0 的
> 完整文本很长，用这个方式最省事也最不容易出错）。

### 一条不可逆的提醒

**密钥一旦提交进 Git 历史，`git rm` 是删不掉的**，必须重写历史
（`git filter-repo`）并强制推送，而且已经 fork 或克隆过的人手里仍有副本。
正确做法是立刻**吊销并轮换**那个密钥。

首次提交前请务必检查 `git status`。
