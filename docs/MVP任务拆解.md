# MVP 任务拆解 · 「一周试玩」

> 目标：用最小代价验证核心假设——**「看着一群有自己打算的人在你身边生活、
> 竞争、结怨」本身就好玩**。
>
> 预估总量 **约 3 周**（单人全职）。带 ⚠️ 的是风险点。

---

## 依赖图

```
  T1 事件总线 ★地基
   │
   ├──→ T2 性格特质 ──┐
   ├──→ T3 稀缺冲突 ──┼──→ T4 记忆与积怨 ──→ T7 回忆档案
   │                  │         │
   ├──────────────────┴─────────┴──→ T5 事件流 ★验证关键
   │
   └──→ T6 情绪气泡

  T8 NPC 私有财产 ──→ T9 锚点日程 ──→ T10 扩容到 6 人
                                        │
                                        └──→ T11 七天节奏 ──→ T12 打磨平衡
```

**T1 必须最先做。** 记忆、事件流、气泡三者本质是同一件事的三种呈现，
先做总线，后面三个几乎是免费的；不做总线就要把「发生了什么」的逻辑写三遍。

## Phase 0 · 地基（0.5 天）

### T1 · 事件总线

**目标**：全局统一的事件出口，所有系统只管 `emit`，订阅方各取所需。

**改动**
- 新增 `EVENTS[]` 环形缓冲（保留最近 N 条，防止无限膨胀）
- `emit(type, {actors, subject, data, day, clock})`
- 现有会产生事件的位置接上：完成行动、社交互动、资源结算、需求见底

**事件类型（MVP 够用）**
```
act.start / act.done / act.interrupted
social.<动作名>            闲聊/称赞/送礼/争吵…
conflict.blocked           想用某物但被占
conflict.taken             想要的资源被别人先拿走
need.critical              某项需求见底
econ.sold / econ.bought
```

**验收**：跑 3 个游戏日，`EVENTS` 里能看到 50+ 条结构完整的事件，
且每条都能追溯到「谁、对谁、因为什么」。

**状态：✅ 已完成**（2 天内 217 条 / 6 类 / 0 残缺，冒烟测试已加断言）

实现中的两个发现：

1. **冲突判定改成「最想要的那个被占才算」**。原本 `decide()` 遇到被占物件直接
   跳过，如果照搬会为每个被占物件都发事件，噪音爆炸。改成先全量打分排序，
   只有排第一的那个被占才 `emit`，再加 60 分钟同目标冷却。
2. **修掉一个潜伏崩溃**。社交动作构造的是「伪物件」（只有 `n/dur/adv`，没有
   `use` 座位数组），玩家社交中途按 T 托管，AI 会拿它去 `score()` →
   `o.use[0]` 直接炸。已在 `score()` 和迟滞重估两处加守卫。

### T1.5 · 承诺规则（计划外，已完成）

事件总线做出来后，行为第一次变成可统计的数据，立刻暴露了一个问题：
**NPC 行动中断率 62%**——改主意比做完事还频繁，事件流会被「改去 XX」淹没。

最初判断是迟滞参数太松，打算调参。**数据否掉了这个判断**：

```
切换时的分数比 ratio 平均 11.12      （阈值只有 1.15）
79 次中断里，真紧急的只有 3 次
30 次是新目标完全不急（需求 > 60）
平均在 33% 进度时放弃，10 次是过半才放弃
```

分数比 11 倍远超任何合理阈值，**调参数不可能有用**。

**根因是结构性的**：`score()` 衡量的是「现在从头开始做这件事值多少」。
行动进行中，被满足的需求在回升，当前行动的分数一路下跌，
而其他选项相对越来越好——**行动越接近成功，越显得不值得继续**。
这个比较从一开始就不公平。

**解法**：开工后只有两种情况允许改主意。

```js
const maySwitch = urgent        // ① 有需求跌破 30 —— 保留"放下手上事去抢灶台"
               || prog < 0.2;   // ② 进度还浅 —— 沉没成本低
```

**效果**

| | 改之前 | 改之后 |
|---|---|---|
| 中断率 | 62% | **17%** |
| 完成次数 | 48 | **68** |
| 不急的中断 | 30 | **1** |
| 紧急中断 | 3 | 4（保住了） |

冒烟测试已加断言：中断率 > 35% 直接红。

> **方法论备注**：这个问题在纯逻辑视角下看不出来——代码没报错、
> 行为也"合理"。是事件总线把行为变成可统计数据之后才暴露的。
> 而且第一直觉（调参数）是错的，靠数据才纠正过来。
> 后续每做一个系统，都值得先问「它产生的事件能量出什么」。

## Phase 1 · 让故事发生（4 天）

### T2 · 性格特质系统（1 天）

**目标**：让 NPC 之间**天生**就有合不来的组合。

现有的 `TRAITS` 只是需求权重（勤奋/享乐/社交/整洁），不产生人际摩擦。
改成两层：

- **需求权重**（保留现有）
- **互斥特质**（新增）——共处时产生摩擦

| 特质 | 与之冲突 | 摩擦表现 |
|---|---|---|
| 洁癖 | 邋遢 | 同处一室时双方心情下降 |
| 话痨 | 孤僻 | 话痨主动搭话，孤僻方关系反降 |
| 吝啬 | 慷慨 | 涉及金钱的事件上互相看不顺眼 |
| 虔诚 | 懒散 | 对方偷懒时会指责 |

每个 NPC 随机 2 条特质，保证阵容里至少有一对冲突。

**改动**：`CAST` 加 `traits[]`；新增 `friction(a, b)` 计算摩擦值；
共处时按摩擦值扣关系并 `emit('conflict.friction')`。

**验收**：给定一组固定种子，两个互斥特质的 NPC 共处 1 小时后关系必然下降，
且事件总线里有对应记录。

**状态：✅ 已完成**

实际实现的四对特质，每对都同时影响【行为】和【关系】——
只做关系修正的话，玩家在画面上看不出谁是谁：

| 特质对 | 行为影响 |
|---|---|
| 洁癖 ↔ 邋遢 | 卫生需求权重 ×1.9 / ×0.45 |
| 话痨 ↔ 孤僻 | 社交需求权重 ×1.8 / ×0.4 |
| 吝啬 ↔ 慷慨 | 家计权重 ×1.6 / ×0.65（慷慨额外 +社交） |
| 急性子 ↔ 慢性子 | 耐心 ×0.55 / ×1.7，直接改承诺规则的松紧 |

实测权重差异达 **8.4 倍**（老莫卫生 3.80 vs 芜青 0.45）。

### 长跑暴露的问题：关系单向棘轮

第一版摩擦没有下限，**第 2 天所有对立关系就触底到 0 并永久卡死**。
到 0 之后关系不再携带信息（分不清「刚认识就不合」和「结怨五十天」），
也没有任何恢复路径。

两处修正：

1. **摩擦地板**：`floor = max(4, 18 - 对立对数 × 6)`。对立越强地板越低，但不到 0。
2. **关系向基线回归**：`rel += (20 - rel) × 0.00009 × dm`。不维护就退——
   **这正好是决策 8「社会位置会滑落」的实现**，一个机制服务两个目的。

修完之后关系有了可读的梯度，且 3 天保持稳定：

```
小满  柯 25  老 24  芜  6*      (* = 有对立特质)
柯林  小 25  老 14* 芜 27
老莫  小 24  柯 14* 芜 12*
芜青  小  6* 柯 27  老 12*
```

### 冒烟测试抓到的一个隐蔽 bug

加断言「对立的关系必须低于不对立的」之后立刻红了：**敌 12 > 友 9**。

原因是 `Math.max(floor, rel - d)`：当关系（8）本来就低于地板（12）时，
这行代码会把它**抬高**到地板——**摩擦反而促进了感情**。

改成只在地板之上才施加摩擦。这个 bug 靠肉眼看日志永远发现不了，
是断言写成「必须有梯度」才逼出来的。

### T3 · 稀缺冲突表达（1 天）

**目标**：把「想用但被占」从沉默排队变成可感知的摩擦。

现状：`decide()` 里发现座位被占，直接跳到下一个候选，**什么都没发生**。

改成：
- 记录「我本来想要 X，但被 Y 占了」→ `emit('conflict.blocked')`
- 该 NPC 对 Y 产生**轻微不满**（进入 T4 的记忆）
- 需求越急，不满越重（饿到 10 还被抢饭 vs 饿到 60 被抢，权重差 5 倍）

⚠️ **注意**：不满值要有**衰减**，否则几十天后所有人互相仇视。
建议半衰期 3~5 个游戏日。

**验收**：故意把床减到 2 张、NPC 保持 4 人，跑 2 天，
必然出现「A 因为 B 占床而不满」的事件链。

### T4 · 记忆与积怨（2 天）★核心

**目标**：让关系值背后**有具体的事**。这是行为变成故事的分水岭。

**数据结构**
```js
npc.memory = [
  { type:'social.gift', from:'小满', day:3, weight:+18, decay:0.02 },
  { type:'conflict.blocked', from:'老莫', day:4, weight:-6,  decay:0.08 },
]
```

**规则**
- 记忆条目有**权重**和**衰减率**：恩情记得久，小摩擦忘得快
- `rel(a,b)` 从「一个数字」改为「记忆条目的加权和 + 基础好感」
- 记忆影响决策：讨厌的人在场时，社交类物件的效用打分下降
- 单人记忆上限（如 30 条），超出时合并同类项为「累计印象」

⚠️ **性能**：6 个 NPC × 30 条 = 180 条，每次打分都遍历会很慢。
关系值应**缓存**，只在记忆变动时重算。

**验收**
- 玩家送礼后，NPC 的档案里能查到「第 3 天，小满送了我礼物」
- 连续抢占同一 NPC 的资源 3 次后，它拒绝与你进行深聊（关系门槛）
- 30 个游戏日后，小摩擦的影响衰减到近乎消失，送礼的恩情仍在

**状态：✅ 已完成**

关键实现决策：**保留 `rel[name]` 字段不变，只换掉它的来源**。
所有读关系的代码（打分、菜单门槛、面板）一行没改，
关系从"存储的数字"变成"记忆的推导值"是透明替换。

衰减用半衰期，直接编码「恩情记得久，小摩擦忘得快」：

| 记忆 | 权重 | 半衰期 |
|---|---|---|
| 送礼 | +22 | 22 天 |
| 深聊 | +15 | 14 天 |
| 争吵 | −20 | 12 天 |
| 特质摩擦 | −9 | 3 天 |
| 被抢资源 | −7 | 1.5 天 |

实测 30 天后：送礼还剩 8.5 / 22，被抢资源衰减到 **−0.0**。

**记忆真的改变行为**：同一张沙发，坐着讨厌的人打分 3.7，
坐着亲近的人 15.6 —— 差 4.2 倍。NPC 会主动躲开合不来的人。

### 标定与结构上的三处修正

1. **基线 20 → 35**。20 太低，3 次小摩擦就归零，深聊门槛（40）永远够不着。
2. **同类递减**：`w = base × 0.62^近两天同类数`。第 1 次被抢 −7，第 6 次 −0.64。
   否则重复摩擦线性累加，又回到单向棘轮。
3. **续怨而非新增**：递减到不足基础值 25% 时，不再新增条目，而是
   **刷新最近同类记忆的时间戳**并标记「（第 N 次）」。
   语义上「他又抢了我一次」本就该是让旧怨不消退；
   实现上也避免记忆表被零分量垃圾撑爆——修完记忆条数从 33/23/30/41 降到 11/14/14/12。

配合 `refreshRel()` 里清理衰减到 0.3 以下的条目，档案现在读起来是这样：

```
老莫 对 柯林（关系 11）
  第1天 慷慨 × 吝啬              -5.7
  第2天 抢了我想用的炉灶          -4.4
  第3天 慷慨 × 吝啬（第 6 次）    -3.2
  第3天 抢了我想用的床            -3.8
```

**「为什么他俩关系这么差」现在有答案了。** 这就是行为变成故事的那一步。

> 另：T2 里的显式「关系向基线回归」已删除——记忆按半衰期衰减，
> rel 自然回落到基线，决策 8 的「不维护就退」由衰减本身实现，不需要额外机制。

### T4.5 · NPC 主动社交（计划外，已完成）

**试玩后暴露的根本缺口：NPC 之间没有交流，也就没有故事。**

排查发现 `SOCIAL` 动作表**只有玩家菜单在用**，`decide()` 的候选里
**只有物件、没有人**——NPC 的社交需求是靠"坐沙发"满足的，
**满足于「物」而不是「人」**，所以他们永远不会主动找人说话。

修法是把「人」也做成候选，和物件一起进效用打分：

```js
for(const o of OBJ) all.push({o, s:score(sim,o), by:occupiedBy(o,sim)});
for(const c of socialCandidates(sim)) all.push(c);      // 人和物一起排队
```

动作选择不用随机数，完全由关系/积怨/性格推导，行为可预测也可复现：

```
积怨深且关系差 → 争吵      关系≥45 且有余钱 → 送礼
关系≥40        → 深聊      关系≥30         → 称赞/开玩笑
其余                        → 闲聊
```

### 三轮失控与修正

**① 争吵正反馈爆炸**：摩擦→积怨→争吵→**争吵又加深积怨**→更想吵。
第一版跑出 **64 次争吵**全在同一对身上，需求告急从 2 次涨到 22 次——
他们顾着吵架不管死活。加了 14 小时冷却 + 需求告急时不找茬 + 分数封顶。

**② 修完变成一次正面互动都没有**。根因是**物件比人更"高效"地满足社交**：
沙发一次给 social 22 + fun 46 + energy 12，闲聊只给 social 18，AI 当然选沙发。
现实里独自坐沙发并不解决社交需求——改成**社交场所只在旁边真有人时才给 social 广播**
（独处时 ×0.2），同时把面对面社交的收益提到压过"待在同一个房间"。

**③ 争吵仍占 63%，村子戾气过重**。打分一比就明白：闲聊 4.6 分 vs 争吵 24 分。
把找茬的驱动力压到同一量级（`min(13, g*0.5)`），并抬高触发门槛。

### 关键设计：争吵是「宣泄」，不是「加深」

最重要的一处改动。原本争吵会**增加**积怨，形成棘轮；
改成争吵时把积攒的小怨气**发泄掉 60%**，只留下一道明确的伤疤（−14）。

```js
function vent(a, bName){
  for(const e of (a.mem[bName]||[]))
    if(e.w<0 && e.type!=='social.争吵') e.w*=0.4;   // 吵完出了气
}
```

这把**棘轮变成了周期**：摩擦累积 → 爆发 → 消气 → 再累积。
戏剧性反而更强，而且关系不再归零。

### 结果

| | 修正前 | 修正后 |
|---|---|---|
| 争吵占比 | 63% | **36%** |
| 社交动作种类 | 1 种 | **5 种** |
| 关系归零 | 3 对 | **0 对** |
| 需求告急 | 22 次 | 9 次 |

村子长出了真实的社会结构：

```
小满  柯 58  老 39  芜 14
柯林  小 62  老 11  芜 56      ← 柯林和芜青成了密友
老莫  小 38  柯  8  芜 21      ← 老莫被孤立
芜青  小 14  柯 56  老 21
```

冒烟测试新增断言：NPC 社交必须发生（≥3 次）、有多样性（≥2 种）、
争吵占比 < 55%、关系不归零。

### T3 稀缺冲突表达

**状态：✅ 随 T1/T4 一并完成**。`conflict.blocked` 在 T1 就已发事件
（含"最想要的才算冲突"的判定和 60 分钟冷却），T4 把它接进了记忆。
不满的衰减由半衰期（1.5 天）实现，符合原计划「半衰期 3~5 天」的意图。

## Phase 2 · 让玩家看见（2.5 天）

### T5 · 事件流 UI（1 天）★验证关键

**目标**：把总线上的事件翻译成人话，滚动展示。

```
第4天 09:12   芜青 抢先占了 工作台，老莫 只好去砍柴
第4天 10:40   你 送给 阿柳 一份礼物   关系 +20
第4天 12:03   老莫 和 芜青 起了争执（洁癖 × 邋遢）
第4天 18:55   芜青 卖出一件家具，赚了 48 金币
```

**要求**
- 三档筛选：全部 / 只看与我相关 / 只看冲突
- 点击某条 → 高亮涉及的角色
- 措辞必须是**因果句**，不是状态播报。
  ✅「芜青抢先占了工作台，老莫只好去砍柴」
  ❌「芜青开始使用工作台」

⚠️ 这条是整个 MVP 里**对验证结果影响最大**的。玩家能不能复述出故事，
八成取决于这里的文案质量。值得多花半天打磨措辞。

**状态：✅ 已完成**

### 核心原则：总线记录一切，事件流只放有故事价值的

`act.start` / `act.done` 占总线事件的 **70%**，但「小满开始床」没有任何故事信息。
加了 `isStory(e)` 筛选：`act.start` 全部剔除、`act.interrupted` 全部剔除、
`act.done` 只保留有产出的（砍木料 / 做家具 / 看完书）。

信噪比：**总线 308 条 → 事件流 57 条**。

### 文案：每类事件都写成因果句

```
第2天 08:56  柯林做好了一件家具
第2天 09:15  你做好了一件家具
第2天 10:02  你卖掉一件家具，进账 48 金币
第2天 10:07  粮店被你占着，老莫只好转去淋浴
第2天 10:25  你嫌芜青邋里邋遢
第2天 11:27  靠窗的床被老莫占着，你只好转去沙发
```

几处关键处理：

- **玩家一律称「你」** —— 代入感差别很大
- **`conflict.blocked` 补上"退而求其次去了哪"** —— 有这个才写得成因果句
- **摩擦按特质对写具体说法**，带方向性：
  「A嫌B邋里邋遢」/「A被B挑剔得不耐烦」/「A等不及B磨蹭」
- **需求告急用口语**：「饿得前胸贴后背」「困得睁不开眼」「快憋不住了」

三档筛选（全部 / 与我有关 / 只看冲突），点某条高亮当事人并切换面板。

### 首次实装暴露的三个文案 bug

1. **「床被老莫占着，芜青只好转去床」** —— 三张床同名。
   改成「靠窗的床 / 中间的床 / 角落的床」，同时加了"退路与被占同名时换说法"的兜底。
2. **「老莫 嫌对方邋遢」** —— 摩擦文案只传了一个名字。
3. **同一对在半小时内反复「不欢而散」** —— 摩擦阈值 45 太低。
   抬到 120 并加同一对 3 小时冷却，摩擦事件从刷屏降到 5 条 / 3 天。

### 顺带修掉一个超卖竞态

面板上出现 **家具 −1**。原因是 `pre`（前置条件）在**决策时**检查，
`eff`（产出结算）在几十分钟后执行——两个 NPC 同时开卖，都通过了检查，
结算时库存变负。经典的 check-then-act 竞态。

修法是**结算时复查**，而且扑空不静默吞掉，转成故事：

```
柯林赶到摊位，家具已经被别人卖光了
柯林到了工作台，木料已经被用完了
```

**失败本身成了叙事材料** —— 这比单纯修 bug 值钱。

冒烟测试新增四条断言：事件流有行、筛选生效（story < bus×0.6）、
文案无自指（「转去X」的 X 不能等于被占的那个）、无占位符残留、无负库存。

取当前最急的需求或最新的强情绪。

**验收**：不打开任何面板，只看画面就能大致判断每个人的状态。

## Phase 3 · 让世界有压力（3.5 天）

### T8 · NPC 私有财产（2 天）⚠️

**目标**：NPC 从「共享家庭资源」变成**独立经济体**，才能成为竞争者。

现状：`home = {money, food, wood, goods}` 是全局共享的。
所有人在给同一个家庭打工——**没有竞争**。

改成：
- 每个 NPC（含玩家）有自己的 `money / inventory`
- 「家计」需求从全局改为**个人**
- 市场是共享的：卖出会**压低价格**，买入会推高（简易供需）
- NPC 的积累持久化，会买东西、会变富

⚠️ **这是 MVP 里风险最高的任务**。改动面大，且会打破现有的经济平衡，
预留调试时间。建议先做一个「只有钱、没有库存」的简化版跑通再扩展。

**验收**：跑 7 天，NPC 之间的财富出现明显分化，且能从事件流看出原因。

**状态：✅ 已完成**

`home` 全局对象一共只有 17 处引用，比预估的小。核心改动是把物件的
`pre` / `eff` 从无参改成**按人**：

```js
// 之前：所有人给同一个家庭打工
pre:()=>home.wood>=2, eff:()=>{home.wood-=2; home.goods++;}
// 之后：各算各的
pre:s=>s.inv.wood>=2, eff:s=>{s.inv.wood-=2; s.inv.goods++;}
```

`eff(s)` 现在可以**返回一条经济事件**，这样售价随行就市也能正确写进事件流。

### 共享市场：卖的人多，价格就跌

```js
mktSell: p *= 0.955   （下限 基准×0.62）
mktBuy:  p *= 1.045   （上限 基准×1.55）
每分钟:  p += (base - p) × 0.0014      // 缓慢回归基准
```

这是「NPC 是真竞争者」（决策 8）真正落地的地方——**你卖得多，行情就被你自己压下去**。

### 标定教训：小市场不能用大市场的弹性

第一版每笔交易撼动价格 **10%**，那是按大市场标定的。这里只有 4 个人、
每天约 3 笔交易，结果贸易条件持续恶化：

```
天 家具 粮价 | 存粮
 1   40   37 | 8/6/7/4
 3   37   39 | 8/3/9/1
 5   34   35 | 4/0/3/0     ← 卖一件家具已经买不起一次粮
```

**卖价跌破买价 = 慢性死亡螺旋**。虽然还没饿死，但趋势是坏的。
把单笔冲击降到 4.5% 并加快回归后：

```
天 家具 粮价 | 饥饿均 家计(4人)     金币(4人)      存粮
 5   42   28 |   60  75/43/77/59    58/5/32/16     9/6/10/8
 5   43   28 |   63  70/39/70/41    1/21/4/61      13/5/11/4
```

家具稳在 42~47（被竞争压在基准 48 之下）、粮价 27~30（被需求推到基准 24 之上），
供需关系正确反映，但不再崩盘。**金币从 1 到 61，财富真的分化了。**

冒烟测试新增：无负账户、价格在带内、贫富差 > 5（否则等于还在吃大锅饭）、
多数人有存粮。

### T9 · 锚点日程（1.5 天）

**目标**：让玩家能计划「去哪找谁」。

```js
npc.schedule = [
  { from: 6,  to: 9,  place: 'home'   },   // 早上在家
  { from: 9,  to: 18, place: 'work'   },   // 白天在工作地
  { from: 19, to: 23, place: 'tavern' },   // 晚上在公共场所
]
```

- 锚点期间：效用打分里**该场所的物件加权**，其他场所大幅降权
- 锚点之间：完全自由，效用 AI 说了算
- 紧急需求（如厕、饿到临界）可以打破锚点——否则会很假

**验收**：连续 3 天，晚上 20:00 去酒馆都能找到至少 3 个 NPC。

**状态：✅ 已完成**

地图上没有独立的酒馆，改成给每个物件打**分区**标签，日程锚定的是区域：

```
home    床 × 3、马桶、淋浴、冰箱
work    林地 × 2、工作台、摊位、粮店
commons 餐桌、沙发、书架、炉灶      ← 晚饭 + 社交都在这里
```

```js
const SCHEDULE=[[6,9,'home'], [9,18,'work'], [19,23,'commons'], [23,30,'home']];
锚点内 ×1.9   锚点外 ×0.32   任何需求 <22 时锚点让位
```

每人有 ±0.8 小时的作息偏移，不然像上下班打卡。

**结果**：20:00~21:30 公共区平均 **2.9 人 / 4**，达标率 **71%**。
锚点遵守度 home 67% / work 45% / commons 70%——**不是 100%，这反而对**：
目的是可计划，不是机械打卡。

### 一个自己制造又自己修掉的回归

加完锚点，中断率从 25% 飙到 **48%**。第一反应是"锚点让分数在时段切换时摆动 6 倍"，
于是让**重估时跳过锚点**——结果更糟，涨到 50%。

用 T1 埋的诊断字段一查才看清：

```
中断构成: 紧急 14 ｜ 刚开始就换 47 ｜ 其它噪音 14
```

**63% 的中断是"刚开始就反悔"**。根因正是我那个"修复"：
`decide()` 用锚点选，重估**不用**锚点——**两套标准**。
刚选完一个区内动作（被放大 1.9 倍），重估看到的是没放大的数字，于是立刻改主意。

改回一致后：

| | 引入锚点前 | 加锚点后 | 修正后 |
|---|---|---|---|
| 中断率 | 25% | 48% | **27%** |
| 完成次数 | — | 87 | **111** |
| 刚开始就换 | — | 47 | **9** |

> 教训：**决策和重估必须用同一套标准**。任何"只在某个环节生效"的修正项
> 都会制造这种"选完就反悔"的抖动。而这一次能定位，全靠 T1 事件总线里
> 顺手埋的 `diag` 字段——没有它只能靠猜。

## T13 八卦传播 ✅（1 天）

**要解决的问题**：玩家的行为只影响当事人。跟老莫吵一架，柯林毫不知情——
玩家是旁观者，不是变量。参考模拟人生 2 的 gossip 系统。

**做法**：A 和 B 友好交谈时（非敌对、时长 ≥20 分钟），A 把自己对第三人 C
最想说的那条记忆讲给 B，B 因此获得一条**二手记忆**。

这是个正反馈系统，会自己滚成"全村互恨"，四道闸门缺一不可：

| 闸门 | 做法 | 不做会怎样 |
|---|---|---|
| ① 二手不转述 | `hand===2` 的记忆不可再传 | 一条消息在人群里无限放大 |
| ② 按信任折扣 | `trustIn(rel)` = 0.22 + rel/100×1.1 | 讨厌的人说的话也照单全收 |
| ③ 亲历者打折 | 听者已认识当事人时 ×0.65 | 道听途说压过亲眼所见 |
| ④ 同事只听一次 | `sid` 去重 + 二手半衰期 ×0.6 | 同一件事反复叠加 |

**定向验证**（`tools/verify-gossip.js`，13 项断言）：
不测"八卦事件发生了"，测**因果链本身**——玩家跟 A 吵架 → B 态度不变 →
A 和 B 聊过之后 B 对玩家变冷淡，且四道闸门逐条可证伪。

实测链路：`B对玩家 35 → 吵架后 35 → 听说后 30.5`，源 -14 传成二手 -4.66。

### 教训一：数值正确 ≠ 玩家有感

第一版信任折扣直接用 `rel/100`。数学没错，但 REL_BASE=35 意味着
"中立熟人只信 35%"，一条争吵传出去只掉 **2 分**——玩家完全感觉不到涟漪，
整套系统等于白做。改成带下限的信任曲线后是 4.7 分。

**现在有一条断言专门守这个设计意图**：`⑬ 涟漪足够被感知(≥3分)`。
可感知性是需求，不是调参口味，所以它该是断言而不是注释。

### 教训二：三天的窗口看不见社会系统的漂移

冒烟测试只跑 3 天，全绿。写了 `tools/longrun.js` 做 14 天开/关对照，才看见：

**① 关系被钉死在 0 和 100**（八卦关掉也一样，是**既有结构缺陷**）。
`rel = clamp(35 + Σ记忆, 0, 100)`——记忆是累加的，clamp 只把溢出砍掉，
到第 14 天关系表不再携带任何信息：送礼不会更亲，吵架不会更僵。
在"无限沙盒"的设定下这是真 bug，只是 3 天时还没攒够量。

改成 logistic 软饱和 `100/(1+e^-((Σ-14.1)/22.75))`：
常用区间几乎还是线性（保住所有已调好的阈值），两端只逼近不触达。

| Σ记忆 | -40 | -20 | 0 | +20 | +40 | +60 |
|---|---|---|---|---|---|---|
| 旧 clamp | 0 | 15 | 35 | 55 | 75 | 95 |
| 新 logistic | 8.5 | 18.3 | 35 | 56.4 | 75.7 | 88.3 |

修完：14 天后关系最低 28.5（原来是 0），最高 98.2（原来是 100）。

**② 八卦绕过了记忆上限**——我自己引入的 bug。`tellGossip` 直接
`push` 进记忆表，绕开了原先内联在 `remember()` 里的 `MEM_CAP` 逻辑，
14 天实测把单对记忆顶到 33 条。抽成 `trimMem()` 让两条写入路径共用。

**教训**：只要多一条写入路径，内联的不变量就会漏。共享不变量必须是共享函数。

### 教训三：内部键值会顺着新通道漏进文案

摩擦记忆的 `why` 存的是原始键 `'洁癖 × 邋遢'`。事件流一直没事，
因为它走 `FRICTION_SAY` 转成人话。但八卦**原样引述记忆的 why**，
于是冒出「芜青跟柯林提起老莫——「洁癖 × 邋遢」」这种调试输出。

加了 `FRICTION_MEM` 表（嫌弃的人和被嫌弃的人记住的不是同一件事），
冒烟测试的文案瑕疵检查加了 `\s×\s` 这条红线。

### 尚未解决：八卦让村子同质化

14 天对照还显示：开八卦后**关系离散度从 95 掉到 70**，争吵占比 20% → 0%。
根因是 `MEM` 表里正面记忆的分量本来就更大（送礼 +22、深聊 +15
vs 争吵 -14、摩擦 -9），八卦挑"最想说的那条"自然偏正面，
加了 1.5× 的负面偏置也没扭过来。

村子变得一团和气 = 没有派系 = 没有故事。**但这个先不调**——
没有"派系结构该多分化"的目标值，调参就是猜。留给试玩后再定。

## T15 事件流降噪 ✅（0.5 天）

**要解决的问题**：跑到第 8 天数一遍事件流的构成，发现赌注输在信噪比上。

| 降噪前 | 降噪后 |
|---|---|
| **抢家具 35%** | 抢家具（升级版）8% |
| 例行采买 11% | 采买 7%（只留涨价时） |
| 砍木料 ~8% | 0（成品和卖出才是故事） |
| 全部社交加起来 24% | **社交合计 46%** |

三分之一的篇幅在讲家具调度。玩家读完只会记得「他们一直在抢沙发」——
系统不是不产生故事，是故事被日志淹了。

**做法不是调阈值，是分层**：事件流是**叙事层**，不是日志层。
总线照旧记录一切（记忆、积怨、诊断全靠它），`isStory()` 只挑读起来像故事的。

- `conflict.blocked` 降级为纯背景。**一天里被同一个人抢到第三次**才升级成
  `conflict.escalated` 讲一句，且每天每对最多一次
- `econ.bought` 只在粮价涨过 1.2 倍时出现（例行采买是流水账，涨价还得买才有压力）
- 砍木料不进事件流（`QUIET_DONE`），保留「做好了一件家具」和「卖掉，进账 44 金币」
- 摩擦一天只讲一次（冷却是 3 小时，一天能触发好几次；对积怨有用，
  但事件流里连着三行「你嫌芜青邋里邋遢」就只是复读）

### 关键约束：isStory 必须是纯函数

`renderFeed()` 每次都重新过一遍整个环形缓冲，所以**不能在 isStory 里用计数器**
——它会随渲染次数漂移。重复判定只能在 `emit` 当场算好，用 `'quiet'` tag 带过去。

### 顺带修的因果倒置

八卦行原本排在引发它的交谈行**前面**，读起来是反的：

```
老莫跟你提起柯林——「花钱大手大脚」     ← 先看到转述
老莫和你聊了很久，交了心（关系 +14）     ← 才看到交谈
```

`gossipExchange()` 挪到 `emit('social.…')` 之后。现在一次对话是一个完整的场景：

```
第7天 14:33  老莫和你聊了很久，交了心（关系 +14）
第7天 14:33  老莫跟你提起柯林——「花钱大手大脚」
第7天 14:33  你跟老莫提起柯林——「送过我礼物」
```

### 新增的三条红线（`smoke-test.js`）

- `feed.blocked === 0` —— 单次抢家具不得进事件流
- `feed.topShare <= 0.35` —— 任何单一类型都不能吃掉三分之一以上篇幅
- `feed.gossipOrder === 0` —— 八卦必须跟在交谈之后

## T16 分区扩图 + 私宅 + 扩容到 6 人 ✅（2.5 天）

**要解决的问题**：玩家反馈「地图不够大」。原来是 18×15 一整块，
4 个人共用 3 张床、1 个马桶、1 个淋浴 —— 那不是村子，是青旅。

**地图 18×15 → 31×24，三层分区：**

| 区域 | 范围 | 内容 | 地面 |
|---|---|---|---|
| 私宅区 | y 1–6 | 六间独立卧室，每间一张**有主的床** | 木地板 |
| 村中心 | y 8–15 | 盥洗×4、厨房、书架 + 中央石板广场（餐桌、长椅） | 草地 / 石板 |
| 工作区 | y 17–22 | 林地×3、工作台×2、摊位、粮店 | 泥土 |

物件 15 → 22，NPC 4 → 6（阿柳、梨梨，精灵表重新生成为 6 行）。

### 私有卧室补完了 T8

`score()` 加一行 `if(o.owner && o.owner!==sim.name) return null` —— 别人的床根本不进候选。

在此之前钱和粮是私有的，床却是公共的，这个不一致就是「抢家具」曾占掉事件流 35% 的
根子。**盥洗和厨房仍然共用** —— 那里的争抢是有意思的，抢床不是。

### 关于"大地图会更空"

这是真风险，处理办法是**让地面有分层**：三种地面 + 两条横街 + 中央广场，
而不是一整块绿地。空间的"身份"来自可辨认的地方，不来自格子数。

**另外：没有做摄像机跟随，全图始终可见。** 这不是偷懒 ——
这个游戏的价值是看社会系统运转，摄像机跟着玩家会把 NPC 的故事挡在视野外。
全图可见对这个类型是特性不是限制。

### 坦白一件事：扩图并不会让时间变稀缺

走路速度 1.6 格/模拟分钟，横穿全图约 20 格 ≈ 12 模拟分钟，
而睡一觉是 240 分钟。**距离在这个尺度上仍然近乎免费。**
要让时间变成资源，还得靠体力条，不能指望地图。

### 踩坑：紧急通道退化成了常开的闸门

扩图后中断率从 30% 涨到 **37%**，超了 35% 红线。

诊断（141 次中断的分布）：p25=10 分钟、中位数 20、p75=70，其中 46% 发生在开始 15 分钟内。
根因不是"早期窗口"，而是承诺规则里的**紧急通道**：

```js
let urgent=false;
for(const k of NK) if(NEEDS[k].dec && s.need[k]<30){ urgent=true; break; }
```

它是个**布尔量** —— 只要有任一需求 <30，就允许换去**任何**更高分的东西。
小地图上无所谓；扩图后走路变多、需求长期偏低，这个闸门几乎常开，
于是「饿着的人被书架从床上拽起来」。

改成**定向**的：紧急通道只对真能解决那个告急需求的候选开放。

```js
const early  = prog < 0.1*patienceOf(s);
const solves = o => urgentK && o.adv && o.adv[urgentK] > 0;
if(best && best.s>cur*1.15 && (early || solves(best.o))){ ... }
```

中断率 37% → **18%**（比扩图前的 30% 还低）。

**教训**：一个"例外条款"在小规模下看起来无害，规模一变就可能退化成默认路径。
布尔型的例外（有没有）比定向型的例外（是哪一个）危险得多。

### 踩坑：断言的采样窗口跟不上规模

扩图后 `relFoes < relFriends` 在第 3 天翻转了（敌 36 / 友 33.2）。
逐日测下来：

| | day3 | day7 | day11 | day14 |
|---|---|---|---|---|
| 敌 | 36 | 37.6 | 39.1 | 42.7 |
| 友 | 33.2 | **50.5** | **67.3** | **75.6** |

机制没坏 —— 是 6 个人 + 大地图让摩擦的**预热期变长**了，
3 天时摩擦记忆才 12 条而正面接触已有 48 条，均值假性倒挂。

处理：冒烟测试改查**机制**（对立的人之间必须真的产生负分量的摩擦记忆），
涌现层面的梯度断言挪进 `longrun.js` 的第 14 天 —— 那里才测得准。
**不是放宽断言，是把它挪到测得准的地方。**

### 意外收获：人多了之后，八卦不再抹平社会结构

T13 时记过一个未解决问题：八卦让村子同质化（关系离散度 95→70）。
6 个人的长跑数据反过来了：

| 关系离散度 | 八卦开 | 八卦关 |
|---|---|---|
| 4 人 | 68 | 95 |
| **6 人** | **91** | **76.6** |

人少时消息很快传遍所有人，形成共识；人多时传播有先后、有信任差异，
反而**制造**结构。这个问题规模一变就自己消失了。

## T17 摄像机跟随 + 手机适配 ✅（1.5 天）

**要解决的问题**：玩家反馈「没适配手机」「最好像星露谷的地图一样」。
这两件其实是同一件 —— 扩图后整张图 744×576，手机竖屏根本放不下，
**必须做摄像机跟随**；而摄像机正是星露谷那类地图的结构。

### 摄像机

- 视口按屏幕算格数，上限 **18×13**（即使屏幕放得下整张地图也不铺满 ——
  一是保证各设备构图一致，二是"镜头跟着走"本身就是这类地图的观感）
- 镜头插值追随（`0.18` 系数）。直接对齐会抖，因为模拟是固定步长的
- 只画可见范围的地砖，不再全图刷
- 世界画完 `ctx.restore()`，菜单和提示改走**屏幕坐标**

### 用小地图补回"看戏"

镜头跟随的代价是看不见全图，而**同时看见所有人在干嘛**本来是这个游戏一半的价值。
右上角 2px/格 的小地图把它补回来：地形、六个人的位置、玩家、当前镜头框。

> **性能坑**：小地图一开始每帧重画 `GW*GH=744` 个方块，
> 实测把单帧位移从 2.4px 顶到 4.8px（帧率掉一半）。地形是死的，
> 烘到离屏画布上一次就够 —— 改完回到 2.4px。

### 手机

| | 做法 |
|---|---|
| 布局 | `@media (max-width:1000px)` 面板从右侧改为堆在下面 |
| 走路 | 左下虚拟摇杆（`pointer` 事件 + 捕获，带死区和归一化） |
| 交互 | 右下「互动」键；菜单行可直接点选；点小人切换查看对象 |
| 提示 | `[E]` 之类的键盘字样在触屏上自动隐藏，帮助文字整段替换 |
| 触屏检测 | `matchMedia('(pointer:coarse)')` → `body.touch` |

### 装饰层：大地图最怕空

草丛、野花、草簇散在草地上，石头和树桩堆在工作区，广场摆花盆。
没有任何玩法作用，纯粹让三个区域看起来像"地方"。
用坐标做种子的确定性伪随机，所以每次刷新长得一模一样 —— 可复现，也好截图对比。

### 踩坑：断点不一致，平板被算成桌面

820px 的平板视口算出来是 **9×23** —— 又窄又高的畸形。

两个原因叠加：① 视口没有上限，`min(w,14)*min(h,11)*sc` 的打分让"高瘦"胜出；
② JS 里的 `mob` 断点是 780px 而 CSS 的 `@media` 也是 780px，
820px 走了"桌面"分支 → 给右侧面板预留了 352px → 可用宽只剩 468 → 9 格。

修法：加视口上限 18×13，并把 JS 断点和 CSS 断点一起提到 **1000px** ——
面板在窄屏是堆在下面的，就不该再给它预留横向空间。

**教训**：布局断点在 CSS 和 JS 里各写一份，早晚会不一致。它们描述的是同一件事。

### 新增 `tools/verify-mobile.js`

5 种视口（手机竖/横、小手机、平板、桌面）逐个验证：
横向溢出、主角是否始终在视口内、镜头是否夹在地图内、触屏控件是否出现、
**摇杆是否真的能让人走起来**（真发 pointer 事件，不是查 DOM 存在）。

> 写这个测试时先自己踩了一次：摇杆五档全"失灵"。
> 排查发现是**测试的错** —— 前一步的按键测试已经把主角推到卧室墙边了，
> 在墙角测摇杆当然走不动。测试得先把人挪到空地。

## T19 种地 ✅（1.5 天）

**为什么值得做**：这是第一个**跨日**的机制。在此之前所有动作都在几十分钟内结算完，
所以第 3 天和第 8 天感觉不出区别 —— 「无跨天累积」这个老问题，种地正好对症。

六块**无主**田，四个阶段：

```
荒 ──开垦──> 耕 ──播种(耗米1)──> 苗 ──浇水×3天──> 穗 ──收割(得米4)──> 耕
```

**生长只在浇过水的那天推进**（浇过 +34/天，没浇 +4）。所以浇水是一份每天都得还的债 ——
时间由此第一次真正变稀缺，而且不靠体力条。

田记下**是谁播的种**。别人抢收会在苦主心里留下 `conflict.harvest`（-26，比吵一架还伤）。

### 实现：四阶段全用 getter

`adv` / `dur` / `note` / `pre` / `eff` 都做成随阶段变的 getter，
所以**效用 AI 一行都不用改** —— 它根本不需要知道"种地"是什么，照常按广播打分。

### 教训一：纯效用 AI 天生做不了「延迟回报」

第一版跑十天，六块田**全是荒的，没人种**。

根因是结构性的：打分函数只看当下的需求满足，而开垦的回报在三天后。
荒田（广播 22，代价还比林地重）被林地（26）严格压制，永远排不进候选。

修法不是抬广播值硬凑，而是**让家计真的包含地里的东西**：

```js
function cropValue(s){        // 长着的庄稼算家底
  v += 7 + f.grow*0.11;
  if(!f.wet) v -= 9;          // 今天没浇 —— 这一项才是关键
}
```

那个**负项**是让「日常维护型动作」在效用 AI 里成立的唯一办法：
没浇水本身会把家计推低、制造紧迫感，人才会回来浇。否则种下去就没人管了。

### 教训二：我自己造的反馈陷阱

改完之后六块田**全熟在地里没人收**。

因为熟了的庄稼还在算作家底 —— "家里有粮"的踏实感恰好压住了去收割的动机。
阿沅账面上"富有"，实际手里只有 2 斗米。

修法：`cropValue` 只算**还在长**的。长着的是指望，割回来的才是粮；
**熟的那一刻家计反而该掉下来**，逼人下地。

### 教训三：无主田 = 人人互偷

再跑，收割终于发生了 —— 但 **83% 都是抢收**（15/18）。
效用函数里没有"这不是我的"这个概念，谁近谁饿谁就割。

跟 T4.5 的 63% 争吵率是同一类问题，需要闸门：

```js
const desperate = sim.need.hunger<25 || sim.inv.food<=0;
s *= desperate ? 0.75 : 0.06;      // 平时几乎不可见，断粮时才重新成为选项
```

抢收占比 **83% → 4%**（14 天 24 次收割里 1 次）。
于是抢收变成**走投无路的人才干的事** —— 那才是有分量的故事，而不是背景噪音。

### 效果

14 天实测：开垦 6、播种 30、浇水 78、收割 24（其中抢收 1）。
**米铺采买从 9 次降到 5 次** —— 种地真的成了替代路径，而不是装饰。

一轮对比：伐木90+木作120+市摊45 = 255 分钟 → 约 44 文（≈4 斗米）；
开荒之后一轮 播种35+浇水×3 75+收割60 = 170 分钟 → 4 斗米，**且一文不花**。
开垦是一次性投入，此后田一直是熟的 —— 先苦后甜，这个梯度本身就是玩法。

### 新增 `tools/verify-farm.js`（13 条断言）

冒烟测试只跑 3 天，而一茬庄稼要 3 天以上，那边看不出循环是否闭合。
这个文件直接驱动状态机，把每条设计意图变成可证伪的断言 ——
包括上面三个坑各自对应的回归项（⑧ 没浇的田要把家计拉低、⑨ 熟了不再算家底、
⑫ 不饿就不动别人的田、⑬ 闸门不能误伤自己的田）。

### 教训：倍率对负分是反向的 —— 我引入的真 bug

打分**可能是负的**（代价大于广播时，比如精疲力尽还去砍树）。
这时候 `s *= 0.3` 会把 −10 抬成 −3 —— **惩罚变成了奖励**，排序整个翻掉。

这个坑不是天气引入的，是一直都在：距离折扣、锚点、抢收闸门、社交好恶
**全部**都是直接乘。只是之前没人去查负分那一侧。

```js
// 正分乘、负分除，两边都保持"系数小 = 更不想干"
const scale=(v,m)=> v>=0 ? v*m : v/Math.max(m,1e-6);
```

五处倍率全改走它。冒烟测试加了一条 `scale(-10,0.3) < -10` 守住方向。

### 教训：天气的"伪随机"有周期

第一版用 `Math.sin(d*12.9898)*43758.5453` 那套 —— 30 天里后半段连着 **12 个晴天**。
换成整数位混淆（xor-shift + imul）后 40 天分布是 21 晴 / 11 雨 / 8 阴，最长连续 6 天。

### 教训：半夜采样看什么都像坏了

16 天长跑后我看到「六块田全熟着没人收」，以为又踩了 T19 那个反馈陷阱。
一查是 **0 时**的快照 —— 锚点在 home、又在下雨，所以打分低；
而六个人里**四个此刻最想干的正是「待割」**，根本没死锁。
改成中午采样：第 6/9/12/15 天午时都是「苗苗苗苗苗苗」，循环一直在转。

**看长跑的截面，得挑对时辰。**

## T24 季节与第二种作物 ✅（2 天）

`对标星露谷.md` 清单上的最后一条。**一季七天，一年二十八天**，
界面从「第 14 日」改成「1年 秋2」。

### 为什么不照抄"冬天什么都不长"

星露谷的季节是**硬窗口**，这才是"计划"的压力来源。但直接照抄会把这个
六个人的小村逼死 —— 存粮撑不住一整季。

改成**两种作物各有各的时令**：永远有东西可种，但**得种对**。

| | 春 | 夏 | 秋 | 冬 | 产量 |
|---|---|---|---|---|---|
| **稻** | 100% | 115% | 55% | **0%** | 4 斗 |
| **麦** | 60% | 50% | 115% | 75% | 3 斗 |

稻是好年景的选择（产得多，但冬天整季停长）；麦是保底（少一斗，但四季都能种）。
于是每到换季，玩家要重新算一次"这一季该种什么"，而不是无脑重复。

播种从一个动作摊开成**选种菜单**，当季不长的那个直接置灰并写明原因：

```
熟田
1. 种稻                      冬季不长      ← 置灰
2. 种麦      冬季长势 75% · 收 3 斗
```

NPC 不需要懂"季节"这个概念 —— `bestCrop()` 按 `生长倍率 × 产量` 排个序就行，
效用 AI 那边一行没改。

### 天气也随季节

冬天阴冷多雨、夏天晴得多。实测四季各 28 天：
夏 20晴/3阴/5雨，冬 10晴/12阴/6雨。**换季不只是数值变了，天色也跟着变。**
季节色调直接盖一层薄色，比重画一套地砖便宜得多。

### 一年跑下来（村子过得了冬）

| | 田 | 六人存米 | 均饥 |
|---|---|---|---|
| 春7 | 稻·全熟 | 7/5/10/5/9/8 | 65 |
| 夏7 | 稻·生长中 | 18/9/20/7/14/13 | 78 |
| 秋7 | **麦**·全熟 | 14/9/17/3/10/27 | 75 |
| 冬7 | **麦**·生长中 | 22/8/27/11/6/29 | 78 |
| 2年春2 | 麦·全熟 | 25/8/24/9/3/18 | 81 |

NPC 自己在秋天换成了麦，没有一个人饿死，存粮反而一路走高。

### 两个 bug

**① `settleEff` 没把 `why` 透传出去。**
`fieldEff` 返回 `{type:'farm.sown', why:f.crop}`，但 emit 时只带了
`who/obj/objId/val/tags` —— 于是事件流里**麦子也写成「种下一茬稻」**。
新加的返回字段，要顺着整条链检查一遍有没有被中途丢掉。

**② `grow` 攒出 `39.099999999999994`。**
时令倍率是小数，累加不取整就会留下浮点噪声，存档和界面上都难看。

### 教训：我把"陈旧"误诊成了"浮点误差"

存档测试 ⑦ 又红了，漂移 0.0104。上一轮我把同类现象归因为浮点误差，**那是错的**。

真正原因：`rel` 是从记忆推导的，但只**每 5 模拟分钟整表重算一次**。
存的是旧值、读档时重算是新值，差的就是一个刷新周期的衰减量。

修法是 `saveGame()` 存之前先 `refreshRel()`。漂移从 0.0104 变成 **0.0000**，
容差也从 0.01 收紧到 0.001。

> 「差得很小」不等于「是浮点误差」。**小的偏差也有确定的成因，值得查到底** ——
> 查清楚之后是能修到零的，放宽容差只会把问题盖住。

### 教训：随手定的比例阈值撑不住系统变化

冒烟测试的特质断言是「至少一半的对立组产生了摩擦」。那个 0.5 是我随手定的，
3 天窗口下本来就在 6/14 和 8/14 之间抖 —— 天气一上线（雨天户外活计打折，
碰面的模式就变了），直接掉到红线下。

改成查机制本身：**摩擦确实发生了（≥2 对），而且总分量是负的**（实测 −53 ~ −64）。
涌现层面的梯度仍由 `longrun.js` 在第 14 天断言。

## T25 地图改成一座小镇 ✅（2 天）

上一版是"三条横带"——一排卧室、一片公共区、一片工地，本质还是宿舍。
这版改成**六户宅院围着一个镇中心**，地图 31×24 → **46×34**。

| | 内容 |
|---|---|
| **每户** | 一间屋（榻、米缸、灶台，**都只有主人能用**）+ 一个带篱笆的院子（一块私田） |
| **镇中心** | 井、茅厕×2、浴堂×2、书塾、茶棚、竹榻、木作坊×2、集市、米铺 |
| **镇东** | 林地×3、**两块公田** |

物件 28 → **40**（私产 24 / 公共 16），田 6 → **8**（私 6 / 公 2）。

### 为什么私田之外还要留公田

上一版六块田全是无主的，"抢收"才成立（T19 那条最有分量的故事线）。
**一旦每家都有围墙，抢收就会随围墙一起消失。**

所以保留两块公田，并且让它**更肥**（多收 2 斗）：
远在镇东三十格、可能被人抢先，换更高的收成 —— 贪心与安稳之间的真选择。
14 天实测公田确实有人种（一块已播、一块已开垦）。

至于抢收降到 0：**太平年月本来就不该有人偷**。
闸门条件是"断粮或很饿"，现在人人有自家田，所以偷不发生 ——
等到哪年收成不好，它自己会回来。这是对的，不该硬凑。

### 篱笆不能画成墙

篱笆挡路但不是夯土墙，得走 `DECOSOLID`（T18 为水井建的那条路），
渲染时从"画成墙砖"的分支里排除，否则整个镇子会被土墙围起来。

### 顺手修的性能

渲染时每格都要判断"这是墙还是家具"，原来是现算 `OBJ.some(...)`——
40 个物件 × 每帧 234 个可见格 ≈ **近万次判断**，而且随物件数线性变差。
物件占地一辈子不变，建一次 `OBJCELL` 表就够。

### 教训：按索引切片的替换会顺手删掉不该删的

改地面分区时我用了"从标记 A 切到标记 B"的替换，
**把中间的整个装饰层（DECO / DECOSOLID / 井）和小地图一起吞掉了**。
页面只报一个 `DECOSOLID is not defined`，修完又冒出 `drawMini is not defined`。

后来是拿备份做**顶层声明的差集**才一次看全的：

```python
decls = set(re.findall(r'^(?:const|let|function)\s+(\w+)', old, re.M))
missing = decls - now        # → MINI_S, ROOMX, drawMini, miniBg
```

**按索引切片替换，必须检查删掉的到底是什么**；
一个个撞运行时错误，只会撞到下一个为止。

### 教训：TDZ 又踩了一次

六户私产要按名字建，我把 `NAMES.forEach(...)` 写在了物件表里，
而 `const NAMES` 声明在三百行之后 —— `ReferenceError: sims is not defined`
（真正的原因是 NAMES 的暂时性死区让整个脚本没跑完）。

跟 T4 那次 `REL_BASE` 是同一个坑：**`const` 写在后面不是"晚一点生效"，是直接抛错。**

### 教训：断言里写死的数字，都是等着假红的

三次冒烟全 FAIL 但每一项指标都正常 —— 是 `farmPass` 写死了 `n === 6`。
改成查关系而不是查数字：**私田人手一块、公田必须还在、状态合法**。

同一轮里 `feed.topShare` 报 35% 也是假警报：3 天窗口只有几十条事件，
单一类型很容易过线；第 8 天量起来是 24%。

## 这一轮的四个坑

### ① 第三次踩暂时性死区

`mkForage()` 在物件表里被调用，而 `FORAGE_SPOT` 是 `const`、声明在几百行之后。
报错是 `Cannot access 'autoPilot' before initialization` —— 表面看毫不相干，
真实原因是整个脚本在 TDZ 处就断了。

**这个项目已经踩了三次**：T4 的 `REL_BASE`、T25 的 `NAMES`、这次的 `FORAGE_SPOT`。
每次都是"新东西要在物件表里用，但声明写在了后面"。
`const` 写在后面不是"晚一点生效"，是**直接抛错**。

### ② 画法名对不上会【静默】画成床

审计发现 **6 个米缸和 2 块公田全都画成了床** ——
`drawObj` 按 id 前缀查 `FURN`，而 T25 把冰箱改名成 `jar`、公田叫 `common`，
表里根本没有这两项，于是静默掉进 `bed` 兜底。

同样的坑 T18 踩过一次（`wc1`/`bath1`）。**逻辑全对，只有截图能发现。**
这次改成显式的 `art` 字段 + **开机自查**：

```js
const miss = OBJ.filter(o => !FURN[artOf(o)]).map(o => o.id);
if (miss.length) fail('这些物件没有对应的画法，会画成床：' + miss.join(', '));
```

让它当场喊出来，而不是等人截图才发现。

### ③ 断言取"第一个 commons 物件"，加个祠堂就假红

锚点断言原本比"第一个 commons 物件 vs 第一个 work 物件的总分"，两个毛病：
`provision` 不在衰减列表里、测试没把它归一，结果随家计状态摆动；
而且物件表一加东西，"第一个"就换人了。

改成**直接量锚点倍率本身**（当季区 ×1.9、非当季区 ×0.32），
挑没有前置条件、也不属于任何人的物件当探针。

### ④ 环形缓冲的头部是测试的盲区

"八卦必须跟在交谈之后"这条稳定报 2 个瑕疵，但单独跑一次都不复现。
把索引打出来才看清：**坏的永远是第 0 和第 1 条** ——
缓冲满 400 之后不断 `shift()`，最前面那两条八卦的"交谈"早被挤出去了。

从第 4 条起才判。另外把四个瑕疵计数**拆开打印** ——
合并成一个数字的时候，红了根本不知道是哪一条。

## T28 钓鱼 ✅（0.5 天）

### 为什么是钓鱼

不是为了"再多一样东西玩"。钓鱼在这里担两个具体的角色：

**① 一条不用米的口粮。** 之前断粮只有两条路：籴米（要钱）、收割（要等三天）。
钱粮同时见底就是死局。烤鱼只要一尾鱼、不费米，钓点又是公共的、不要本钱 ——
这是垫底的那条后路。

**② 让雨天第一次变成好事。** T23 做完天气之后，下雨只有两个效果：
田不用浇了（省事），露天活计打折（碍事）。玩家对雨的反应永远是"今天少干点"。
现在雨天鱼口好（空手率 42% → 30%，同样竿数多进四成），
于是"今天下雨"从**少干点活**变成**改去钓鱼**。

> 星露谷里天气的真正用法不是惩罚，是**改道** —— 下雨那天你不去农场，
> 你去矿洞。一个变量同时制造变化、运气和"今天该换个活法"。

`weatherMul()` 里因此多了一条在所有户外折扣之前的分支：钓点雨天 **×1.55**，
而林地/田/市摊照旧 ×0.72。这两条必须一起测，否则很容易在加成时把别人的惩罚改坏
（verify-fish 的 ⑦⑧ 就是一对）。

### 设计细节

| | 做法 | 为什么 |
|---|---|---|
| 鱼种 | 鲫（四季）/ 鲤（春夏）/ 鳜（秋冬） | 季节硬窗口，和作物同一套逻辑 |
| 稀有度 | 用**得鱼尾数**表达（1/2/3） | 库存只有一个 `fish` 计数，稀有度没有别的地方可放 |
| 空手 | 生手晴天四成，宗师雨天不到一成 | 手艺第四次真的有用；也让"白坐一个时辰"成为味道而不是 bug |
| 随机 | `hash01(天,时辰,钓点)` | 全项目不用 `Math.random`，重放一致、测试对得上 |
| 出路 | 烤鱼（不费米）/ 鱼羹（费米更顶饱）/ 集市卖鱼（会跌价） | 口粮、升级版、换钱三条，各有代价 |

### 这一轮的三个坑

#### ① 广播了 `provision`，却没兑现

钓点 `adv:{provision:30}`，但 `provision()` 只算米、钱、地里的苗 ——
钓一天鱼家计纹丝不动。效用 AI 不会报错，它只会**永远上同一个当**：
分数很高、去了、需求没变、下一轮分数还是很高。

**广播和结算对不上，是这套 AI 最阴的一类 bug。**
凡是新物件带 `adv`，就得回头确认那个需求真的被 `eff` 抬得起来。
（verify-fish ⑨ 就是钉这条。）

#### ② 塘差点把一户人封死在自家院里

塘原本摆在 `y12..14 / x35..40`。而 `y=12` 是上排宅院的院墙线，
`x=40` 正是那户**唯一的院门**（篱笆三面到底，`x===9` 处留一个门）。
水一压上去，老莫就再也出不了自家院子 —— 而这**不会报错**，
表现只是"这个人整天在院里发呆"。

因此新加了 `tools/verify-map.js`：从每个人的床做洪水填充，
断言**每个座位人人走得到**、**没有人被封死在自家院里**。
并且做了反向对照（把塘按错误位置摆回去，第⑤条确实变红）——
测不出错的测试没有用。

这条测试同时收编了以前散落的几种地图事故：物件画成床、座位被挡、

## T29 用不了也要说一声 ✅（0.3 天）

试玩反馈：**「公共设施怎么有些没有交互」。**

### 不是没做，是没说话

查下去发现 `nearby()` 的第一行就是：

```js
if(o.pre && !o.pre(PC)) continue;   // 条件不满足 → 这个物件整个消失
```

于是开局走到镇中心，**木作坊和集市连提示都没有** ——
因为身上没木料、没木器。座位被 NPC 占着也一样一片空白。
玩家看到的是「这些设施没做完」，实际上是做了、只是一个字都不说。

> 星露谷从来不藏：矿车照样能点，只是告诉你「需要 5 个铜锭」。
> **沉默是最贵的 UI**——它把「暂时不行」和「根本没做」变成了同一件事。

改法：`nearby()` 不再过滤，改为永远返回并附一句原因，三类各有说法。

| 原因 | 提示 |
|---|---|
| 条件不满足 | 「集市 · 手里没木器也没鲜鱼可卖」「木作坊 · 要木料×2（现有 0，去镇东伐木）」 |
| 座位被占 | 「浴堂 · 有人正用着」 |
| 别人的私产 | 「米缸 · 这是阿沅家的」 |

能用是金色 + `[E]`，用不了是灰色 + 原因；按 E 会把原因弹在头顶，
而不是静默吞掉这一下。「为什么」写在物件自己身上（`why`），
不是集中判断 —— 集中判断迟早漏一个。

### 顺带抓出来的两件事

**① 私产闸门只管 NPC，不管玩家。** `score()` 里有 `if(o.owner && o.owner!==sim.name) return null`，
但那是 AI 的路径；玩家走的是 `nearby()`，**从来就没有这道闸门**。
也就是说玩家一直可以随便用别人家的米缸、灶台和私田 ——
而 verify-farm 的第⑯条「私田只有主人看得见」测的是 `score()`，测不到这条。
**同一条规则有两条执行路径，就要测两次。**

**② 水井是纯装饰。** 广场正中最像公共设施的东西，走过去一声不吭 ——
玩家第一个去戳的就是它。收编成真物件（打水盥洗，洁净 38 / 22 分钟），
广场原本一个洁净点都没有（浴堂远在镇西），它补的正是这个空。

### 一个差点放过去的连带塌方

井的第一版做成了「社交场所」（`social:true`，社交 26 / 30 分钟）。
冒烟测试立刻红了：**摩擦 0 对**（之前 2~4 对）。

查下去是井把**茶棚整个吃掉了**——四天里茶棚零次使用。
井短时、高回报，NPC 顺手一用就走；茶棚要坐 70 分钟。
可**对立的人只有坐在一起久了才会起摩擦**，这条链子一断，
八卦系统就没有原料，整个差异化空转。

> 加一个「更划算」的物件，可能会悄悄杀死一个**承担叙事职责**的物件。
> 效用 AI 不会报错，它只会去分数更高的地方。

两处修正：井降级成顺手用的水龙头（洁净 38 / 社交 8 / 22 分钟，不再 `social:true`）；
茶棚补强成真正「说话的地方」（社交 42 / 闲趣 24 / 茶点 14，60 分钟）。
摩擦回到 2 对 / 合计 −16.7。

### 测试

`verify-map.js` 加三条，都是这次的复发防线：

```
✓ ⑧ 没有物件会静默消失（用不了也要出提示）
✓ ⑨ 玩家也点不动别人家的东西
✓ ⑩ 带条件的物件都写了「为什么」
```

第⑩条是防「以后加物件只写 `pre` 忘了写 `why`」——
那样只会得到一句无用的「现在还用不了」。

## T30 卡住了要能自己出来 ✅（0.2 天）

试玩反馈：**「人物卡在茶棚无法移动」。**

### 一个没写出来的前提

玩家移动用的是分轴判定，好处是贴着墙能滑动：

```js
if(free(nx, s.py)) s.px = nx;      // 只换 x
if(free(s.px, ny)) s.py = ny;      // 只换 y
```

它有个从没写出来的前提：**人当前那一格必须是通的**。
一旦人物中心落进实心格，`free(nx,s.py)` 读的是当前那一行、
`free(s.px,ny)` 读的是当前那一列 —— **两个同时为假**，
四个方向全堵死，站在那里再也动不了，而且什么都不报。

扫了一遍这张图：**「进去就出不来」的格子有 319 个**（所有墙体和物件的内部）。

### 进去的路不止一条

| 入口 | 怎么发生的 |
|---|---|
| 瞬移到被挡的座位 | `tryInteract()` 直接把人挪到 `o.use[0]`，**从不检查那一格通不通**。T27 的井正好压着茶棚的西座，按一下 E 就卡死 —— 这次报的应该就是它 |
| 读旧档 | 存档存了 `px/py`，而地图每个版本都在改。版本号只在字段变了时才升，坐标失效它管不着 |
| 新物件盖住站位 | 加一个物件就多一片实心格，正好压着谁站的地方 |

堵住其中一条不算修好。**真正的修法是：无论怎么进去的，都能出来。**

```js
function unstick(s){            // 站在实心格里就往最近的空地推出去
  ...  // 由内向外一圈圈找，最多找 8 格
}
```

每步对**所有人**查一次（托管模式下 PC 走 AI 那条路，寻路同样出不来；
NPC 也可能被新物件盖住），读档之后再统一查一次。
玩家被挪动时头顶弹一句「挪出来了」，不装作没事发生。

顺带把入口也堵上一个：`blockReason()` 第一条改成
「座位被挡 → 过不去」，被压住的座位不再报成可用。

### 教训

> **"这种情况不会发生"不是理由，"发生了也能恢复"才是。**

这个坑的三条入口里，我只想得到一条（被挡的座位），
另外两条（旧档、新物件）都是事后才想明白的。
如果只修那一条，剩下两条会在以后某次改地图时原样复现，
而且症状一样隐蔽：不报错、不卡死进程，只是那个人站着不动。

### 测试

`verify-map.js` 加两条：

```
✓ ⑪ 掉进实心格能自己挪出来（茶棚内部/夯土墙/塘/井，五个点）
✓ ⑫ 被挡住的座位不报成可用
```

## T31 人物画细三倍 ✅（0.5 天）

试玩反馈：**「人物不够好看，像素分辨率高些」。**

### 症结不在画，在整条渲染链是 1:1

以前的链路是：世界按 **24 像素一格**画进画布 → 画布用 CSS **整数放大 PXS 倍**。
桌面 PXS=3，所以人物那 **32×42 个像素**，每一个在屏幕上是 **3×3 的大方块**。

放大看就明白了：脸糊成一团、手看不见、两条腿是一坨黑、四帧走路几乎没差别。
**不是画得不好，是根本没有地方画。**

### 修法：不是把人画大，是把同样大的人画细

引入渲染倍率 `RS`：**画布后备存储放大 RS 倍**，绘制前统一
`ctx.setTransform(RS,0,0,RS,0,0)` —— 所有世界坐标一行都不用改。
人物则换成 **96×126** 的原图，直接 1:1 画进放大后的画布。

`RS` 取 **3**，正好等于桌面原来的 CSS 放大倍率。于是：

| | 之前 | 现在 |
|---|---|---|
| 屏幕上一格 | 72 CSS px | **72 CSS px（不变）** |
| 视口 | 15×11 格 | **15×11 格（不变）** |
| 人物占屏 | 96×126 px | **96×126 px（不变）** |
| 人物**像素数** | 32×42 | **96×126（9 倍）** |
| 文字 | 3 倍放大的 9px | 真正按 3 倍分辨率渲染 |

**屏幕上的尺寸一点没变，变的只是密度。** 这正是"分辨率高些"该有的意思。

手机上更划算：视口 15×13 @PXS=1，后备存储 1080 px 被 CSS 缩到 360 —
在 DPR=3 的屏幕上正好 **1:1 命中物理像素**。

### 三个坑

#### ① CSS 放大倍率必须是 RS 的整数倍

`CSS倍率 = PXS / RS`。RS=3 时 PXS=4 会得到 1.33 —— 像素大小忽 1 忽 2，
一眼就脏。所以档位从 `[4,3,2,1]` 改成 `[3,2,1]`。

但**缩小没关系**：那是超采样，在高 DPI 屏上反而正好。
手机 PXS=1 / RS=3 就是这种情况，比以前更清楚。

#### ② 精灵图的一帧高必须整除 RS

生成器出的是 96×**125**，而世界里一帧占 42 格 × 3 = **126**。
差 1 像素就得缩放，缩放就糊。补成 126（空的补在**上面**，脚底对齐不能动）。

顺带把生成器的超采样倍数从 8 提到 12：`pixelize` 要求
`超采样宽度 % 输出宽度 == 0`，而 `8×64=512` 除不尽 96，`12×64=768` 正好 8 倍。

#### ③ 地面撒成了纯色

地砖原本烤在 24×24 上再整体放大，颗粒是 3×3 的方块。
改成按 RS 烤之后我全撒了 1 像素的细沙 —— 结果地面**反而平了**，
远看就是一片纯色。

> 地面的手感靠的是**粗颗粒**，分辨率只是让它边缘更利落。

改成两种一起撒：粗颗粒保持原样（`RS×RS` 大小、原数量），
再叠一层 1 像素的细沙。

### 连带要改的两处测试

两条断言都在**用后备存储的坐标量世界坐标**，画布一放大就错：

- `smoke-test` 的菜单像素断言：`getImageData(menu._x, ...)` 要乘 RS，
  否则量的是画布左上角那一小块，绘制率掉到 8%，看起来像"菜单没画出来"。
- `verify-mobile` 的镜头/视口断言：`cv.width` 换成 `VPW`。
  同时**加了两条新的**：后备存储必须正好是 `VPW*RS`（对不上就说明 fit() 和
  渲染变换脱节），CSS 倍率必须是整数或缩小。

> 改渲染管线时，**测试里的坐标系也是要改的代码。**

## T32 建造 ✅（1 天）

在这之前，玩家能改变的只有**自己的库存**——地图是只读的。
建造是第一个让玩家真正改动世界的系统，也是这个项目**第一个由玩家自己定的目标**
（祠堂那份清单是我定的）。

### 四样东西，没有一样是新发明的

每一样都接在已有的循环上。这是刻意的：新系统的价值在于**让旧系统重新有意义**，
而不是在旁边再开一条互不相干的线。

| | 造价 | 干什么 | 接的是哪条循环 |
|---|---|---|---|
| **水渠** | 木16 + 30文 | 挨着的田每天自动浇灌 | 解掉「每天回来浇水」那道苦役 |
| **腌坛** | 木8 + 20文 | 山货×2 → 腌货×1（卖 40，鱼才 16） | 把采集接进经济 |
| **工棚** | 木12 + 40文 | 自家的木作坊 | 省掉往返镇上 |
| **新田** | 木6 + 25文 | 院里再开一块地 | 种地规模化 |

木料只能从镇东伐木来（90 分钟 +2），**一条水渠就是八趟山**。
这是这个游戏第一次有"我想要那个东西，所以我今天去砍柴"的结构。

水渠尤其值得说：星露谷的洒水器之所以是里程碑，不是因为它省时间，
而是因为它**把一件天天要做的事一次性买断**。在这之前技能只是"干得快一点"，
现在第一次出现了"这件事以后不用做了"。

### 最要紧的一件事：地图从此是动态的

以前「座位不被挡」「每户出得了自家院子」是**启动时校验一次的静态性质**，
`verify-map.js` 一跑就完事。现在玩家能亲手把老莫封死在他院里、
把自己砌死在门内 —— 而且**不会报错**，只会有个人从此站着不动。

所以那套连通性检查从测试里**搬进了游戏本体**：

```js
function connectivityOK(cells){       // 假设这几格被堵上，村子还走得通吗
  const seen = floodFrom(祠堂座位, cells);
  for (每个物件的每个座位) if(!seen.has(座位)) return false;
  for (每个人的当前位置)   if(!seen.has(位置)) return false;
  return true;
}
```

`buildCheck()` 的最后一道就是它。实测：沿着自家院门内侧那一排一格一格建，
**十四格里恰好只有院门口那一格被拦下**，提示「这么一堵就把路封死了」。

> 检查写在游戏里，测试只是去驱动它。
> 一条规则如果只活在测试里，玩家就能在运行时违反它。

### 读档顺序：一个很容易漏的坑

田的状态是**按 `FIELDS` 下标**存的（`fields:FIELDS.map(...)`），
而"新田"会改变数组长度。所以读档时必须**先 replay 建造，再套田的状态**——
顺序反了整片田的状态就会串位：小满的稻苗跑到老莫的田里，而且不报错。

`wipeBuilt()` 也得干净：格子放回 `solid`/`OBJCELL`、水渠从 `DITCH` 摘掉、
新田从 `FIELDS` 里摘掉。漏一样，读两次档建筑就会翻倍。
（verify-build 第⑮条专门钉这个。）

存档版本 6 → 7。

### 操作

桌面 **B** 开兴造菜单 → 方向键挪光标 → **E** 落成，**Esc** 取消。
手机多了一个「造」键，选好之后**点地图选格子**，再按「互动」。
光标是半透明的实物预览：能建描绿框、不能建描红框，**并且写明为什么**
（「差 16 根木料」「只能建在自家院里」「门前得留一格站人」「这么一堵就把路封死了」）——
和 T29 定下的规矩一致：**用不了也要说一声。**

### 测试

新增 `verify-build.js`（22 条）。最要紧的三组：

```
✓ ⑦ 院门那格建不了（不能把自己砌死）
✓ ⑦ 一整排里恰好只拦下门口那格
✓ ⑧ 建完村子处处仍走得通
✓ ⑬ 田的状态没有串位（读档顺序对）
✓ ⑮ 再读一次建筑不会翻倍
```

一个自己写测试时踩的坑：⑥ 一开始断言「浇过的田 grow ≥ 100」，红了。
其实一天浇透只涨 34（三天才到 100）—— **是我量错了，不是代码错了**。
改成断言机制本身：浇了 34、没浇 4，差得出来就对。

## T33 再加五样可建的 ✅（0.6 天）

T32 那四样都长得一样：私人的、1×1、建在自家院里。这次特意每一样都**多打开一个维度**，
而不是再堆四个"跟腌坛差不多的东西"。

| | 尺寸 | 造价 | 新在哪 |
|---|---|---|---|
| **药圃** | 1×1 | 木10+30文 | **解开季节锁**：药草野外只有冬天有，拿钱把"等一年"换成"今天就有" |
| **鸡棚** | 2×1 | 木14+50文 | 第一个**多格**建筑；第一份**睡一觉就有**的产出（每天两枚蛋） |
| **水车** | 2×2 | 木24+80文 | 第一个**有依赖**的建造（必须挨着水渠）；把浇灌半径 1→2 |
| **镇·凉亭** | 2×1 | 木18+60文 | 第一个**公共**建筑：不挂 owner，NPC 真的会来 |
| **镇·义仓** | 2×2 | 木30+100文 | 第一件**利他**建造：捐两斗，第二天施给镇上最饿的人 |

### 几条设计上的取舍

**蛋卖 22 文，腌货卖 40。** 不花力气的东西不该最赚钱 ——
鸡棚是"睡一觉就有"，腌坛要你先进山采两样再回来腌。价差就是这个意思。
蛋的出路在菜谱：蛋羹**不费米**（和烤鱼一样是断粮的后路），蛋炒饭才是好菜。

**水车什么也不产。** 它只是把已有的水渠变得更好用。
"升级已有的东西"和"再加一样东西"是两种不同的成长感，而前者这个项目一直没有。

**义仓对玩家没有任何好处。** 捐两斗米进去，第二天施给最饿的那个人，仅此而已。
它的效果只在事件流里看得见（「义仓开了粥棚，芜青讨到一口热的」）——
但这恰恰是这个项目的差异化：**这里的 NPC 是真的会饿死的**，
所以"给别人饭吃"才是一件有分量的事，而不是一个成就点数。

**凉亭是第一次改变别人的生活。** 到这为止玩家改的都是自家院子。
凉亭不挂 owner，所以 NPC 的 `score()` 看得见、真的会去坐 ——
也就是说玩家能亲手改变村子的社交拓扑：多一处说话的地方，
八卦就多一条传播路径。（T29 的教训在这里也适用：加一个高分社交点，
可能会把茶棚吃掉。凉亭的 dur 和茶棚接近，社交量略低，是刻意压的。）

### 校验器要跟着长

T32 的 `buildCheck()` 只会看一格。这次补了三件事，每件都对应一个新维度：

```js
buildCells(d,x,y)   // 占哪几格：w×h 全都要查
buildSeats(d,x,y)   // 门前那【一排】都要留人（2 格宽就是两个座位）
d.need(x,y)         // 依赖：水车必须挨着水渠，不满足就说「水车得挨着水渠」
```

分区也从"只能自家院里"变成两种：私人建筑查院子，公共建筑查广场 `PLAZA`。
建错地方会明说是哪一种（「只能建在镇中心广场」）。

连通性那道闸门原封不动 —— 只是现在传进去的是**整片格子**而不是一格。
2×2 的义仓比 1×1 的水渠更容易堵路，这道闸门的价值反而更大了。

### 每加一张表，就要在 wipeBuilt 里加一行

`DOLE`（义仓存粮）。它们和 T32 的 `DITCH` 一样，**漏清一张，读两次档就翻倍**。

```js
MILL.clear(); DAILY.length=0; DOLE.n=0; DOLE.stock=0;
```

`DAILY` 还要连**余量**一起存（`daily:DAILY.map(d=>d.left)`），
否则关掉页面再打开，今天的蛋能再拾一遍。存档版本 7 → 8。

**轮子的识别度全在轮辋上** —— 沿圆周铺一圈小方块之后立刻就对了。

## T34 工具 —— 顺带挖出三个「够不着」的系统 ✅（0.8 天）

起因是一句提问：「工棚可以建工具吗？」

答案是不能——但查下去发现了一件更要紧的事。

### 一、三个写好了却点不出来的系统

`tryInteract()` 决定要不要弹菜单的那一行是：

```js
const multi = (EXTRA[n.o.id]||[]).length > 0;      // 只认 EXTRA 表
```

而 `EXTRA` 里只有床、书塾、竹榻。于是：

| 系统 | 做于 | 实际状态 |
|---|---|---|
| 灶台的**菜谱清单**（9 道菜） | T26 | 弹不出来，永远做 `bestRecipe` |
| 熟田的**选种**（稻/麦） | T24 | 弹不出来，永远种 `bestCrop` |
| 祠堂的**四季供奉清单** | T27 | 弹不出来，**而且祠堂连 `eff` 都没有** |

祠堂那条最狠：按 E 只是干站 40 分钟，供奉**永远不会发生**。
也就是说 T27 写的「目标结构」——这个项目补上的最后一块拼图——
从交付那天起就是死的。文档写着 ✅，测试全绿，玩家一次都点不到。

`openObjMenu()` 里那三段特判代码，**从来没有被调用过**。

**根因是同一份判断写了两遍**：`openObjMenu()` 知道哪些物件有多种做法，
`tryInteract()` 又自己判断了一次，两处一开始就没对齐。修法是抽出唯一的来源：

```js
function menuList(o){ ... }                       // 一个物件有哪些做法
function hasMenu(o){ return o.id==='shrine' || menuList(o).length>1; }
```

「能选的多于一样才弹菜单」——米缸只有"取些冷食"，就该直接开做，弹菜单是噪音。
祠堂特判，因为它那唯一一行本身就是清单。

> **入口和内容必须来自同一个地方。** 分开写，就会出现"功能做完了、
> 测试全绿、文档打钩，但玩家够不着"这种最难发现的故障。

### 二、顺手修的老账：玩家吃不到自己的手艺折扣

`runMenu()` 里有 `o.skill ? Math.round(v.dur*skillSpeed(PC)) : v.dur`，
但 `tryInteract()` 那条路径**压根没乘**。于是钓点（`skill:true`）的工时折扣
NPC 吃得到、玩家吃不到 —— 手艺练到宗师，玩家钓一竿还是 60 分钟。

现在统一走 `playerDur(o, base)`：手艺 + 工具一起算。宗师钓一竿 60 → 40 分钟。

### 三、工具

查下来，**这个游戏最耗时的那件事恰恰是唯一永远不会变快的事**：
`tree` 的 eff 就是 `s.inv.wood += 2`，90 分钟一趟，而且没挂 `skill`。
T32/T33 之后木料是全局瓶颈（义仓 30 根 = 十五趟山），这条平线就特别扎眼。

在木作坊或自家工棚打，一次性、永久：

| | 造价 | 改什么 |
|---|---|---|
| **铁斧** | 木4+60文 | 伐木 2→3 根，工时 90→70 |
| **锄** | 木3+40文 | 田里的活省三成工时（25→18） |
| **鱼篓** | 木3+30文 | 空竿 30%→20%，偶尔一竿两尾 |
| **背篓** | 木2+35文 | 采集 2→3 样 |

**NPC 不吃工具。** 六个人的经济是按"每趟 2 根木料"调平的，
给所有人加一档等于整体通胀，好不容易压住的贫富差和抢收率会全变。
所以 `hasTool(k, s)` 第一件事就是 `s===PC`。

打过的工具从清单里消失，并显示在面板的「家什」一行，和手艺并排。

### 测试

新增 `verify-tool.js`（20 条）。**前五条比工具本身重要**——它们钉的是"入口存在"：

```
✓ ① 灶台弹得出菜谱（T26 起就够不着）
✓ ① 祠堂弹得出供奉清单（T27 起就够不着）
✓ ① 熟田弹得出选种（T24 起就够不着）
✓ ① 只有一种做法的不弹菜单（米缸）
✓ ② 祠堂供奉真的能完成
✓ ⑦ NPC 不吃工具（经济不被整体抬一档）
✓ ⑪ 玩家现在也吃得到手艺的工时折扣
```

又踩了一次"我量错了"：④ 一开始断言"当季不长的那行是灰的"，红了——
春天稻麦都长，本来就没有灰行。改成测**对比**：春天两行都亮，
把日子推到冬天，「种稻」必须变灰（稻的冬季倍率是 0）。

存档版本 8 → 9。

### 三个踩过的坑

#### ① 三户挨着排 = 一条南北向的巷子都没有

第一版把三户排成 x=1/20/39，结果**相邻两户的院墙共用同一列**，
那一列从上到下全是实心的。于是北山只能绕到地图最东头才上得去。

改成 x=1/22/43，两户之间空出 x=20 和 x=41 两列——这才是真正的巷子。
**"墙挨着墙"和"墙之间留一格"，在拓扑上是两张完全不同的地图。**

#### ② 扩图会把旧的差事一起拉长

第一版把镇中心带铺到 72 格宽，量了一下：从小满家门口到茶棚 42 步、到公田 66 步。

真正远的只留北山。同时镇边留两棵树和一处采集：**近的稀、远的密**——
北山是"值得专门跑一趟"的地方，而不是"你现在必须跑那么远才有柴烧"。

#### ③ 距离折扣的系数是跟地图大小绑死的

`1/(1+d*0.035)` 里的 0.035 是按 46×34 调的。放大之后，

`mkQuarry()` 在建物件表时就往 `DAILY` 里 push，而 `DAILY` 声明在几百行之后——

`verify-build` 第⑦条原来测「沿院门内侧建一整排，恰好只拦下门口那一格」。
现在院子有**南北两个门**，堵掉南排是允许的——旧断言测的是单出口的拓扑。

不是"封死"，混在一起数就白测了。

## T37 恋爱与成家 ✅（1.2 天）

### 两条红线

**① 不加新数值。** 这个项目的关系是从记忆推导的（`relFromMemory`），
再挂一根"好感度进度条"就等于把已有的那套架空——和 MBTI 那次一样的判断。所以：

| | 怎么来的 |
|---|---|
| 陌生 / 相识 / 交好 | 由 `rel` **读出来**，是连续量的一个离散读数 |
| 相恋 / 结发 | 是**事件**，双方都要点头，存在 `PAIR` 里 |

「走得近就自动结婚」是不行的：那样关系就没有分量了。
门槛也必须是**双向**的——一厢情愿点不动，这是"关系有分量"的全部意思。

而且分两层：`rel`（攀谈一百次也能涨）和 **`intimacy`**（只数深谈、馈赠、相好）。
**攀谈一百次不是感情。**

**② 成家必须有机制后果**，否则又是一枚勋章。四条，每条都接在已有系统上：

| | 接的是哪里 |
|---|---|
| **私产互通** | T29 那道 owner 闸门，多一句 `o.owner!==spouseOf(...)` |
| **家计合一** | `provision()` 改成算两个人的一本账 |
| **吃醋** | 不另做系统——写进配偶的记忆，八卦那套自然会把它传到耳朵里 |
| **孩子** | 每天要哄；不哄双亲掉闲趣和精神。孩子不是勋章，是每天都要还的一笔账 |

### 差异化：NPC 自己会谈恋爱

`pickSocial()` 里加了两行，门槛和玩家**完全一样，不给 AI 开后门**：

```js
if(canWed(sim,t)) return by('求亲');
if(canWoo(sim,t)) return by('示好');
```

十四天的自动跑（玩家全程托管、不插手）：**两对成了，一个孩子出生。**

> 星露谷里 Abigail 和 Sebastian 之间永远不会发生任何事。

### 三个坑，一个比一个隐蔽

#### ① 聘礼先扣钱、后判资格

结算的第一行就是 `if(a.cost) s.money -= a.cost;`，
等走到 `canWed()` 时里面那句"钱够不够"**已经被自己扣成不够了**——
于是**钱照扣、亲永远成不了，而且不报错**。
二十天的自动跑里两对情侣一直停在"相恋"，就是这么来的。
（`makeWed()` 里还会再扣一遍，双重收费。）

修法：资格在扣钱**之前**判好，聘礼只由 `a.cost` 扣一次。
`verify-love` 第⑤条专门钉这个：`paid === WED_COST`，不是两倍。

#### ② 求亲拿不到驱动力

`socialScore()` 里，非敌对动作的分数 = `soc × 社交需求的紧迫度`。
而求亲发生的时候人往往社交需求正高（跟对象天天在一起），
分数只有 **0.05**，永远排在"该吃饭了"（4.6）后面。

> **人生大事不是"我今天有点闷"驱动的。**

所以和吵架同理，给它一条独立的驱动力（示好 16 / 求亲 22）。
不会失控——`canWoo`/`canWed` 那两道闸门很严，而且做完这个动作就消失了。

#### ③ 门槛调了三次，界面上的说明忘了跟着改

菜单里写着「双方关系 ≥ 62」，代码里已经是 72。
改成从常量拼出来（`'双方关系 ≥ '+LOVE_REL`），以后再也不会对不上。

顺带第五次暂时性死区：`SOCIAL` 表里写 `cost:WED_COST`，
而 `WED_COST` 声明在几百行之后。报错是
`Cannot access 'running' before initialization`——又一次和真凶毫不相干。
（REL_BASE / NAMES / FORAGE_SPOT / DAILY / WED_COST。）

### 平衡：门槛调了三轮

| | 第一版 | 现在 | 为什么 |
|---|---|---|---|
| 示好 | 关系 62 / 交心 18 | **72 / 32** | 自动跑里**第 3 天**就有人相恋——关系涨得太快，得靠交心卡住 |
| 成亲 | 关系 75 / 相恋 3 日 | **82 / 5 日** | 同上 |
| 聘礼 | 80 文 | **25 文** | NPC 钱包常年 0~65 文（卖了木器立刻籴米），80 文等于把成亲卡死在一个几乎不出现的瞬间 |

> 门槛该压在**关系**上，不该压在一个本来就贫穷的经济里。

### 一条断言搬了家

冒烟测试的「三天里至少两对起了摩擦」一直在 **0 对和 6 对之间跳**：
三天的社交样本量本来就只有 6~12 次，对立的两个人碰不碰得上是运气。

这不是放宽，是**搬家**——摩擦的方向性由 `longrun` 的 14 天特质梯度去钉
（那里才测得准：敌 67.6 < 友 75.7），冒烟这边只守两件三天内稳定成立的事：
真起了摩擦分量必须是负的、关系不许触底。

### 测试

`verify-love.js`（20 条），最后一条是差异化本身：

```
✓ ⑤ 聘礼只扣一次（不是两次）

```

### 摇篮：孩子从一条记录变成地图上的真物件

2. **菜单是玩家专用的** —— `menuList()` 里写死了 `PC`，

> T34 修过一次（菜单入口），这次是同一个形状换了个位置。

改成**从院子中间往外找**：按到中心的距离排序，摇篮落在看得见的地方。

## 下一步：外观素材库 → 生老病死 → 孩子成人

试玩时提的思路是对的：**头/上身/下身各一套素材库，按种子组合**。
而 `rig.py` 其实已经做了一半 ——
它是 `体型(5) × 五官(眼/眉/嘴) × 发型 × 服装 × 调色板` 的参数化骨架，
五官用**头部归一化坐标**描述再映射到实际头框，所以换体型五官会自动跟着走。

缺的是两件：

| 缺什么 | 怎么补 |
|---|---|
| 组合是手写的（`CAST` 表六个人一个个填） | 改成**按种子展开**：种子 → 各层选项 → 一个角色 |
| 出的是烘焙好的整张图，运行时拼不出新面孔 | 离线把种子展开成**一张多行图集**，游戏里外观 = 种子 → 行号 |

**不改成运行时分层绘制**：那会丢掉 12 倍超采样出来的像素质量，
而这正是 T31 花了一整天换来的东西。

代价是体积：现在 6 行 96×126 是 87KB base64，**每多 6 行约 +90KB**，
16 行会让单文件从 160KB 涨到约 400KB。

**这套图集真正被需要的时刻是「生老病死」**——有人走了就得有人迁入，
迁入的人要有脸。所以它和②一起做，而不是先空放在那里占体积。

③「孩子成人」排在最后，理由也在这：**没有死亡，第七个人只是多一个劳动力；
有了死亡，孩子才是这个村子唯一的延续方式。**

## T39 生老病死 + 外观图集 ✅（1.5 天）

### 先说「饿死」那个词

它在诊断行里挂了几十天，其实只是
`sims.filter(s=>s.need.hunger<5).length` —— 一个计数，**掉到 0 也不会死**。
这一版把它变成真的。

### 不做生日簿

一年 28 天，活到七十是一千九百多天 —— 那种"寿终"玩家一辈子看不到。所以：

| | |
|---|---|
| **年岁** | 只是**初始条件**：决定体质封顶。老莫 61 岁封顶 71，芜青 19 岁封顶 100 |
| **体质** | 饿着 −8、熬着 −5、病着 −6；吃饱睡好 +4，但回不过年岁定的封顶 |
| **疾病** | 从**体质弱 / 身上脏 / 天时不好**来 —— 全是已经存在的量，不新开变量 |
| **死** | 体质归零。**死因是照顾不周，不是生日到了** |

三十天的自动跑（玩家全程托管）：**老莫（六个人里体质封顶最低的那个）
死于"亏了身子"，阿桑搬进了他空下来的宅子，两对成了亲，两个孩子出生。**

顺带让两样一直没什么用的东西有了用处：**洁净**（脏容易病）和**药草**
（榻上的「将养」，一剂病即愈——药草在这之前只是一味菜料）。

### 外观：素材库 + 种子

`rig.py` 本来就是参数化骨架（体型/发型/五官/服装/调色板各一套，
五官用头部归一化坐标描述），缺的只是**把组合从手写变成按种子展开**。

```python
def gen_look(seed, adult=True, old=False)   # 种子 → 一副长相
def build_atlas(out_dir, size, n)           # 展开成 n 行图集
```

两条约束：**服制要自洽**（襦裙配挽发和簪，短打配短发，道袍配长须的老者），
**用确定性哈希不用 random**（同一个种子永远同一张脸，和这个项目
"不用 Math.random"的规矩一致）。

**不改成运行时分层绘制** —— 那会丢掉 T31 花一整天换来的 12 倍超采样质量。
代价是体积：图集从 6 行扩到 16 行，单文件 169KB → 442KB。

### 最容易漏的一环：空宅不是无主之物

私产的 owner 现在**跟着宅子走**（`HOMEOWNER[i]`），所以继承和迁入
只要改一个数组。但人一没，`HOMEOWNER[i]` 变成 `null`，
而 owner 闸门只挡"**有主**且不是我的" —— 于是**全村都能进死者家里睡觉**。

```js
if(o.homeIdx!=null && !HOMEOWNER[o.homeIdx]) return null;   // 单独挡一道
```

`verify-life` 第⑥条专门钉这个：空宅的榻和田，**六个人一个都用不了**。

### 一局结束就是结束

玩家亡故会弹终局屏（享年、在村里过了多少天、身后留下谁、膝下几个孩子）。
但第一版**死后还在自动存档**：关掉页面时 `pagehide` 会把"死后的村子"存下去，
而那份档里**没有 `isPlayer`** —— 读回来 `PC` 会静默变成花名册里的第一个人。
**你重开一局，发现自己成了老莫。**

修法：`saveGame()` 在 `ending` 之后直接返回，`die()` 里顺手 `wipeSave()`。

（这个 bug 也把测试的顺序坑了一次：先存档再杀玩家，存的那份被 `wipeSave` 抹了。
终局那一段只能挪到读档之后做。）

### 阵容不再是常数

`sims` 从写死的六个人变成会增会减的花名册。波及面比想象的小，
因为关系表、记忆、事件流本来就是**按名字**索引的 —— 真正要补的只有三处：

1. `mkSim()` 工厂（新人要能凭空造出来）
2. 存档里加 `roster / homeowner / gone`，读档时重建 `sims`（老存档没有就保持原阵容，向下兼容）
3. `PC` 从 `const` 改成 `let`

### 第六次暂时性死区

`const YEAR = SEASON_LEN*4`，而 `SEASON_LEN` 声明在**几千行之后**。
这次的根因不是"忘了顺序"，是**常量散落在各自的功能块里，谁也说不清哪个在哪一行**。
权宜之计是写死 `28` 并注明来源；真正的修法是把常量集中，那是另一件事。

### 测试

`verify-life.js`（20 条）。存档版本 11 → 12。

```

✓ ② 体质越弱 / 身上越脏，越容易病
✓ ③ 病人格外想躺着（不给 NPC 开特例，只放大"歇着"）
✓ ④ 一剂药草病即愈（药草第一次真有用）
✓ ⑤ 死了是真的从村子里消失

✓ ⑦ 新人有自己的长相 / 性格 / 人格，住进那座空宅

```

## T40 孩子成人 ✅（0.6 天）

地基三样在 T39 就位了（`mkSim()` 工厂 / 16 行图集 / 花名册进存档），
所以这一版只剩两件事 —— 而两件都是**设计取舍**。

### 取舍一：遗传什么

**脸遗传不了。** 图集是离线烘焙的，运行时混不出一张"像爹又像娘"的脸，
除非把每一行的调色板导出来在 canvas 上做像素级重映射 —— 那是另一天的工程。

**但脾气可以混，而且在这个游戏里脾气才是真正看得见的东西。**

```js
mbti:  四个字母，每个字母随机取自父母中的一方
trait: 取自一方
tt:    父母各出一样
```

ENFP 的爹 × INFJ 的娘，十二个种子跑出来是 `ENFJ / INFP / ENFP / INFJ` ——
**每个字母都来自父母，而且混得出双方都没有的组合**。这才叫遗传。

> 断言差点写成一句恒真式：`mbti !== 爹 || mbti !== 娘`。
> 除非父母人格完全一样，这句永远成立，等于什么都没测。
> 改成跑十二个种子，测的是**机制**：字母永远来自父母 + 混得出新组合。

### 取舍二：住哪

成年要有自己的宅子。**有空宅就接手（比外人优先），没有就出外谋生。**

于是「你家孩子能不能留在村里」和「村里有没有人过世」是**同一条线**：

```
老人过世 → 宅子空出来 → 要么外人迁入，要么自家孩子接手
```

这才叫延续，也顺手解决了"村子会不会无限膨胀"——不会，六座宅子是硬上限。
五十天的自动跑里：三对成了亲、两个孩子在摇篮里、**一个孩子长大后因为没有空宅，
出外谋生去了**。

孩子快成年时（差三天内）空宅会**给他留着**，外人不抢先。

### 顺带

- **出生就起名**：事件流、摇篮的名字、面板，在他长大之前就得叫得出这个名字
- **血亲不通婚**：父母、子女、兄弟姐妹都排除。测的时候特意让孩子和亲爹、
  和一个外人攒到**同样的关系（都是 100）**，再看一个能示好、一个不能 ——
  只测"跟爹不行"是不够的，得证明拦住他的是血缘而不是关系不够
- 面板多一行**出身**：「阿柳 与 阿沅 之子」

### 测试

`verify-grow.js`（14 条）。十三项测试全绿。

```
✓ ② 没空宅就出外谋生（村子不会无限膨胀）
✓ ③ 孩子快成年时空宅给他留着，外人不抢先
✓ ④ 十二个种子里每个字母都来自父母
✓ ④ 混得出双方都没有的组合（不是照抄一方）
✓ ⑤ 血亲不通婚：跟亲爹不行 / 同样的关系，跟外人可以
```

### 三件事做完了

| | |
|---|---|
| ① 地图上看得见 | T38：摇篮成真物件，NPC 父母会自己哄；头顶亲缘标记 |
| ② 生老病死 | T39：年岁/体质/疾病/亡故/迁入；16 行外观图集；玩家终局 |
| ③ 孩子成人 | T40：脾气遗传、接手空宅、血亲不通婚 |

现在一局完整的自动跑长这样：**相识 → 交心 → 相恋 → 结发 → 生子 → 哄大 →
老人过世 → 孩子接手他的宅子（或者出外谋生）→ 外人迁入**，
全程玩家一次都不用插手。

## T41 孩子看得见、也留得下 ✅（0.5 天）

起因是一句话：**「孩子怎么没出现在 NPC 列表里」**。

查下来两件事都不算 bug，但两件加在一起就是个坏体验：

1. 摇篮里的孩子**不在 `sims` 里**（他是 `KIDS` 的一条记录），花名册按 `sims` 渲染，
   所以他理所当然不在列表里 —— 而玩家没有任何地方能看到他。
2. T40 的规则是「有空宅就接手，没有就出外谋生」，而六座宅子**开局就是满的**。
   于是绝大多数局里，孩子长到十六天**就直接消失了**。

> 这是"设计说得通、玩起来说不通"的典型：规则自洽（村子不会无限膨胀），
> 但玩家看到的是**养了十六天的孩子凭空没了，连个交代都没有**。
> 规则没错，错的是**上限定在六**，以及**过程全程不可见**。

### 一、看得见：花名册里加上摇篮

```
★ 小满  阿沅  老莫  芜青  阿柳  梨娘   ← sims
◦ 阿囝                                 ← KIDS（灰的）
```

点开是一张孩子卡：**爹娘是谁 · 出生第几日 · 还有几日成年 · 今日哄没哄 ·
成年后住哪**。最后一项最重要 —— 它把原来那条藏在代码里的规则摆到台面上。

还有两处顺带：亲缘那一行现在写「膝下一子 阿囝（6 日，再 10 日成年）」；
成年**前三天**事件流会预告一次：「阿囝再过三日就成年了 —— 住你家的厢屋」。

> 预告的触发条件一开始写的是 `day - born === GROW_UP - 3`。
> 跨日一次可能跳好几天（测试里就是 `day += 16`），等号那天根本踩不到。
> 改成标记位 + `>=`。**"恰好那一天"在跳步的世界里是不成立的假设。**

### 二、留得下：一座宅子住得下两个人

```js
const HOMECAP = 2;          // 户主 + 一个成年子女
```

归宿从两条路变成三条：**空宅 → 爹娘家还有铺位 → 出外谋生**。

留下的那个**不是户主**：他睡厢屋的**铺盖**（`adv.energy` 60，户主的榻是 78）。
同住一宅，米缸灶台私田共用，**铺位各归各的**：

```js
function houseShare(o, s){ return o.homeIdx!=null && o.homeIdx===s.home && !o.priv; }
```

`priv` 只挂在榻和铺盖上。**"自家人"这件事，一个 getter 就够了** ——
所有权闸门本来就有两条执行路径（`score()` 和 `blockReason()`），
所以这个判断也照例要在两处各加一次（T29 的老教训）。

成家不搬家，爹娘**各有各的宅子**，所以一对夫妻其实能留下**两个**孩子 ——
村子上限从 6 变成 12，仍然是硬上限。六十天自动跑：**6 人 → 10 人**，
四个孩子住进厢屋，三个还在摇篮，老莫亏了身子过世，阿桑迁入他的宅子。

### 三、宅子有了继承

户主亡故，原来是「有配偶归配偶，否则空着等迁入」。
现在中间多一层：**宅里还住着人（成年的孩子）就由他接手**。

于是这条线终于闭合了：`生 → 住厢屋 → 爹娘过世 → 接手家宅 → 自己的孩子住厢屋`。

### 踩到的

- **铺盖是绕过建造校验直接放进屋里的一格实心物**。建造有连通性闸门，它没有。
  测试里补了一次全图可达性 —— 屋里就那么几格，堵一格是真的能把床封住的。
- **孩子进的是哪个爹娘的家**，第一版写死了 `a.home`（`key` 排序后的第一个），
  于是断言里的"米缸共用"查的是另一户的米缸。**别假设 `key` 的顺序有语义。**
- **`e.target` 不再是那个 `<b>`** —— 名字里套了个 `<span>·厢</span>` 之后，
  点在标记上就没反应了。改成 `closest('[data-i],[data-kid],...)`。
- **仓里那份 `tools/build_sim.py` 是旧的**。`cd tools && python3 build_sim.py`
  跑的是它，产物少了 4KB，测试红了半天 —— 生成器有两份拷贝就迟早会踩。
