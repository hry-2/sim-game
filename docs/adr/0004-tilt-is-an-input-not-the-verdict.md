# 点头：翻转不是判定，只是判定的两个输入源之一

点头的游戏循环只认**判定**（猜中 / 跳过）这一个抽象事件。
下翻/上翻和点击屏幕下半/上半是**两个平级的输入源**，
各自把判定喂进同一个循环 —— 循环里没有任何一行代码知道传感器的存在。

## 为什么值得记一笔

因为它看起来是反的。这是一款**卖点就是翻转手机**的游戏，
未来读代码的人会预期陀螺仪在核心，结果发现核心是个不认传感器的状态机，
而点击那条路看上去像个可有可无的降级分支 —— 很容易被当成"历史包袱"顺手删掉。

它不是降级分支，它是**这款游戏能被自动验收的唯一原因**。

## 被这条决定逼出来的两个事实

**一，真机上只有 HTTPS 能玩。** iOS 13+ 的 `DeviceOrientationEvent` 要求
在用户手势里调 `requestPermission()`，且页面必须是安全上下文。
`npm run dev` 起的 `http://<局域网IP>:5173` 大概率拿不到传感器事件 ——
真机实玩基本只有 GitHub Pages 那条路。（这条待真机复核。）

**二，柜子里每款游戏都有零依赖的离线验收脚本**（`tools/verify-*.js`，挂在 `check:*` 下）。
判定逻辑如果长在传感器回调里，`verify-nod.js` 就只能去伪造 `deviceorientation` 事件、
连带把角度门限和去抖一起仿真 —— 那是在验收一套仿真器，不是在验收游戏。
抽出判定之后，验收脚本喂的是"猜中/跳过"，跟手机怎么拿一点关系都没有。

## 被否掉的选项

**只做翻转，没权限就报错不让玩。** 它更诚实地表达了"这游戏就该这么玩"，
但代价是：桌面上没法调试、CI 里没法验收、
而且把一款派对游戏的可玩性押在一个**会被 iOS 静默拒绝**的权限上。

## 后果

- 角度门限、去抖、回中判断全部关在输入层里，游戏循环不碰。
- `verify-nod.js` 验的是判定层（计时、不重复、总结统计），**不验传感器**。
  传感器那一层只能靠真机手测，这是已知的验收缺口。
- 哪天想加第三种输入（蓝牙自拍杆、语音"对/过"），改的是输入层，循环不动。
